# Guided setup

Opening the app goes straight to `/onboarding` while a workspace's setup is incomplete; there is no account to create. Setup proceeds through an AI choice, data import, and a suggested ontology (the Ontology step). Selecting Local, Claude, or OpenAI and pressing **Continue** immediately opens the Data step; hosted choices require an API key. Saving the choice and checking the provider happen in the background. Confirming the ontology builds the workspace and publishes it; there is no review page. The server records completion alongside the publication transaction, and setup then opens Home, which shows key metrics picked from the published data. Old dashboard links open Home too.

The workspace stores optional `onboarding` metadata. Import jobs, encrypted provider preparation jobs, assistant runs, and proposals use the existing resource store. No migration is required. Save and finish later opens Data, and Overview offers Resume setup. Closing the browser does not cancel work. Worker leases recover interrupted jobs; upload content is flushed to persistent storage before its job is committed. Include the incoming directory as well as datasets and HelixDB in backups while jobs are pending.

## Data and AI

A connection can select up to 100 tables or S3 files. Each selection creates an existing source and a snapshot job. Only explicitly selected items import. Database snapshots and REST pagination must finish completely, within the existing limits (two million streamed records, 1,000 REST pages, 256 MB per upload). Large or failed imports are never replaced with sample data. Each upload becomes a durable asynchronous job; multiple files can be chosen together. A failed job can be retried, canceled, corrected, or explicitly removed from the setup selection. Removing an input does not delete it or stop an already-running import.

Local AI checks the release-pinned model, pulls it if needed, verifies its digest, and tests structured output. Preparation progress survives reloads. Hosted credentials are encrypted and tested before activating the chosen provider. Existing provider settings remain active if a replacement fails; no provider fallback occurs. Advanced settings in Settings expose models, endpoints, and budgets; onboarding keeps those controls hidden. No preparation job card is shown in onboarding. Failed saves or provider checks show a retry and an option to change the AI choice, while imported data remains available.

**Continue with sample data** highlights the imitated sources for a second and opens the Ontology step while the samples keep loading (`POST /demo` with `advance`). The Ontology step shows the tables arriving, then asks `/ontology` for a suggested ontology: entities consolidated across sources by matching keys, and the links between them. It is computed deterministically from the data; when AI is ready, a background run only rewrites its summary, descriptions and link names. **Looks right — build my workspace** confirms it, with optional renames and exclusions, and starts the build; the confirmed entities and links become records and relationships without a model call, and the model only designs the dashboard. The step then shows the build's progress in plain stages, and while publishing how many records it has read (the run's `progress.records`), with Stop until publishing starts (publication finishes once started, and the cancel endpoint refuses it with 409) and Retry. Nobody reviews the result, so widgets whose SQL still fails after two repairs are left out, as are failing actions and any confirmed pipeline, type or relationship that fails validation. If a dashboard repair call itself fails, the build keeps the widgets that work instead of failing. When no widget remains, the dashboard is replaced by a computed overview that needs no model: the most connected entity's record count, records per entity, and new records per month when an entity has a created or date column. The validated build is published as the user who confirmed the ontology (or who last retried it), and the run succeeds with "Workspace published"; if it still fails validation or cannot be published, the run fails with the reason and setup offers Retry, or Back to the suggestion. Confirming the same choices again restarts a failed or stopped build, like Retry, as does confirming a build that was waiting for the former review page. Each retry continues from saved checkpoints with a fresh model-call budget; the daily token budget still applies. The server still records the `review` step once the ontology is confirmed; the UI shows it as part of the Ontology step. Confirmed renames and exclusions are returned as `ontologyEdits`, so reviewing the suggestion again starts from them, and notes about excluded entities are dropped from the build. When no table has a column that identifies its rows, the suggestion has no entities and confirming it builds dashboards only (their overview counts each table's rows). A second `/demo` while samples load waits for the running load rather than loading them again.

Recommendations use the same bounded, masked assistant orchestration as builds. Their dataset/column evidence is checked, their model usage is accounted for, and their results are cached by input signature. Setup builds exactly one dashboard, which stays available to the API and SDK; the app no longer shows dashboards and uses Home's key metrics instead. All SQL, keys and relationships pass the existing validator before publication. A build from a `goal` without a confirmed ontology (`POST /build`) still waits as a proposal for review and is published with the proposal publish endpoint; conversational revisions produce a new tested proposal.

The setup input signature includes selected sources, immutable dataset versions, pending schema changes and incomplete imports. Changed goals invalidate the selected build. Publication checks this signature, the selected run, permissions, proposal hash, input versions and published generation inside the commit. Retesting definitions retains their setup provenance. Ingestion API arrivals are picked up automatically, excluding explicitly removed inputs. Ingestion replaces complete snapshots; it is not an append API.

## API and SDK

All routes are under `/api/v1/workspaces/:w/onboarding` and require workspace access. Routes marked (write) reject read-only API tokens:

| Method | Route                 | Purpose                                                                                                                                    |
| ------ | --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| GET    | `/`                   | Server-derived progress, readiness, imports, recommendations, build and dashboard                                                          |
| PATCH  | `/`                   | Save step, deferred state, goal and excluded input IDs; no writable completion flag                                                        |
| POST   | `/provider`           | Queue the chosen provider; optional `advanceToData` atomically saves the Data step (write)                                                 |
| POST   | `/sources`            | Test and import explicit selections, with an `operationId` (write)                                                                         |
| PUT    | `/sources/:id`        | Correct an existing connection and queue a fresh import (write)                                                                            |
| POST   | `/uploads`            | Stage one multipart file; requires `Idempotency-Key` (write)                                                                               |
| POST   | `/imports/:id/retry`  | Retry a stopped import (write)                                                                                                             |
| POST   | `/imports/:id/cancel` | Stop pending work (write)                                                                                                                  |
| POST   | `/recommendations`    | Request/cache recommendations for complete selected snapshots (write)                                                                      |
| POST   | `/build`              | Build a `goal` as a proposal for review, optionally revising `parentId`; with a confirmed ontology it builds from it and publishes (write) |
| POST   | `/ontology`           | Compute (once per input signature) and return the suggested ontology (write)                                                               |
| POST   | `/ontology/confirm`   | Confirm the suggestion by `hash`, with `excluded` and `names`, then build and publish                                                      |

Existing provider, source, upload, ingestion, assistant, proposal and publication endpoints remain compatible. The SDK adds `onboarding`, `updateOnboarding`, `prepareProvider`, `importSources`, `correctSource`, `uploadForSetup`, `recommendOutcomes`, `prepareOutcome`, `retryImport`, and `cancelImport`. Run cancellation/resumption and proposal publication use the existing SDK methods. OpenAPI is available at `/api/docs`.

## Verification

`pnpm test:browser` starts an isolated API, executor, and Vite on ports 3101, 3102, and 5174. It uses an in-memory metadata store, `.data/browser-isolated`, and a deterministic local-provider protocol fixture, while executing queries against real DuckDB. It never uses the live HelixDB, provider credentials, or demo archive. Browser artifacts include desktop and 390px setup screenshots. The fixture is only registered in the test server.

Run `pnpm typecheck`, `pnpm test`, `pnpm build`, and `pnpm test:browser` with Node 24. Connector integration tests remain separately opt-in; use isolated MySQL/Helix instances for them.
