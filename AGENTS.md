# Helix Foundry: agent guide

The Helix Foundry site, in two builds: the hosted site, foundry.helix-db.com (branch `main`) and dev.foundry.helix-db.com (branch `dev`) on Vercel, and the local build that `local/` runs on one machine. A Next.js 16 app that serves three things:

- the Foundry UI: a single-page app (react-router 7, TanStack Query), mounted client-only;
- sign-in: helix-website's WFE-brokered WorkOS flow, run as the Foundry AuthKit application;
- `/papi`: a same-origin BFF that forwards an explicit allowlist of WFE routes with the session's bearer token.

Foundry's API is `backend/` (Backend, below): `helix.foundry.v1`, every route under `/v1/foundry` and `/v1/workspaces/{workspaceId}/foundry`. Hosted, the Helix WFE serves those routes beside its own, which the site also calls (whoami, workspaces, members, projects, tenants, billing). Their REST contract is vendored in two parts, Foundry's in `contract/foundry.swagger.json` and the WFE's own in `contract/wfe.swagger.json`, with the ontology agent's Read and Ask JSON Schemas, whose JSON Foundry carries as strings, in `contract/ontology_agent/` with their `VERSION`. `pnpm contract:sync` copies Foundry's contract and the schemas from `backend/`, and the WFE's from `WFE_REPO`, a checkout of hosted Helix's backend, which only Helix's maintainers have.

Next.js 16 differs from older versions. Read the matching guide in `node_modules/next/dist/docs/` before using an API you have not used here.

## Rules

- **The allowlist.** The browser reaches the WFE only through routes listed in `src/server/papi-allowlist.ts`: one entry per method and path, written exactly as in the swagger, with `{param}` matching one path segment. No wildcards, no prefixes. Add only routes the UI calls. Never add sign-in, SSO management, role changes or member removal. `tests/unit/papi-allowlist.test.ts` fails unless every entry is in the contract and served by the mock.
- **WFE types** live in `src/shared/wfe.ts` only, written from the swagger, under a heading per area. grpc-gateway JSON is camelCase, enums are names, int64 are strings, and default values may be missing.
- **Agent JSON** (Read results, Ask events and results) is the engine's, typed from `contract/ontology_agent/` in `src/shared/foundry-read.ts` and `wfe.ts` "Ontology: questions", and parsed without trust. The mock emits exactly those shapes, and `tests/unit/agent-contract.test.ts` validates every mock answer, every fixture and the reads the SPA sends against the schemas (`mock/agent-contract.ts`, ajv), so a contract change fails CI.
- **Calls** go through `api()` in `src/web/api.ts` with WFE paths (`api("/v1/whoami")`). It adds the CSRF header on unsafe methods and sends a signed-out user to sign-in.
- **Look.** Everything uses the kit, shell, tokens and copy tone (`src/web/kit`, `src/web/shell`, `src/web/workspace.css`). Build a new screen from the kit and an existing area's CSS rather than inventing styles, with colors as tokens. Do not edit the kit to suit one screen.
- **Colors** are `--hf-*` tokens in `src/web/workspace.css` only: the light set on `:root`, the dark set in two identical blocks (`@media (prefers-color-scheme: dark)` under `:root:not([data-theme="light"])`, and `:root[data-theme="dark"]`). A new color gets a value in all three, or is listed in `SAME_IN_BOTH`. No other CSS has a color literal; `tests/unit/theme-css.test.ts` checks that, and the dark theme's contrast (4.5:1 text, 3:1 icons and marks).
- **Cookies** are Foundry's own and host-only: `__Host-foundry-session` (`WORKOS_COOKIE_NAME`), `__Host-foundry-csrf`, `__Host-foundry-login-<flow>`. On loopback http (mock, e2e) they drop the `__Host-` prefix. Never set a cookie domain.
- **Secrets** never go in the repo. `.env.example` names the variables. The values in `mock/env.ts` are mock-only fixtures.

## Adding an area

An area (Workspace, Data, Ontology) owns its folder (step 1) and adds to four shared files, each in a section of its own (steps 2 to 5):

1. `src/web/areas/<area>/`: `index.tsx` (route components; Data and Ontology export a `*Routes` table for their URL prefix, and Ontology also `ExploreRoutes` and `AskRoutes` for `/explore` and `/ask`), `paths.ts` (URL helpers, merged into `src/web/paths.ts`), `shell.ts` (sidebar children, a section's panel and command-palette sources), and its CSS.
2. `src/web/main.tsx`: the area's routes, if it adds a new prefix.
3. `src/server/papi-allowlist.ts`: one line per WFE route the area calls, in the area's section.
4. `src/shared/wfe.ts`: the payload types, under the area's heading.
5. `mock/routes/<area>.ts`: the same routes with in-memory state, spread into `mock/routes/index.ts`. Use `membership()` from `mock/state.ts` for workspace-scoped routes and `onReset()` for the area's state.

Then add the area's main flow to `tests/e2e/` and its logic to `tests/unit/`.

## Things to know

- Names and Records: wherever an entity shows (the Explorer's canvas, tooltips, inspector and search, Records, an entity's page, a document's view) it reads by the version of the load the page reads (`explore/naming.ts`, `useNaming(versionId)`; Other data reads by the current load's version): the first non-empty `names` prop of its type, else its key props joined, else its stored `name`, else a short id; a label the version doesn't know, or no current version, keeps the raw label and the explorer's own caption. `<prop>__nn` (normalized names), an entity's `entity_key` and `norm_name`, a fact's `fact_key`, anything's `foundry_load` and Foundry's other stamps (`foundry_*`, such as `foundry_tx`) on all but Foundry's own labels never show in property lists; those stamps (`isFoundryStamp`) also never match the Explorer's search or take its `contains` scan's keys. Records (`/explore/{id}/records`, `areas/records`) is the Explorer's table view: its types are listed in the Explorer's panel (above the table while the panel isn't on screen); every query in `records/model.ts`, each bounded (a page is `range` over one type, one row more than a page, at most 10,000 rows deep; searches and filters count up to 1,000).
- **Running Foundry locally**: `local/` (compose, README, `.env.example` of optional overrides) runs the local build, with nothing to set up: `docker compose up -d --wait` from the root (its `compose.yaml` includes `local/compose.yaml`: one project, `helix-foundry`, the same volumes from either place, and Compose reads `local/.env` for that file from either) or from `local/`. Its first service, `init-secrets` (`foundry init-secrets` in the foundry image, offline), writes the secrets the `secrets` volume lacks, once: an old install's `FOUNDRY_*` from its `local/.env` (setup.sh's, before 0.1.1), else random ones; every other service waits for it and reads its own from the volume (the site `FOUNDRY_LOCAL_TOKEN_FILE`, MySQL `MYSQL_PASSWORD_FILE`, the store its file, foundry `local.secrets_dir`). The connector key there seals every stored credential and is never made again. foundry makes the owner's first workspace, My workspace, until the install has had one, and with no `FOUNDRY_AI_PROVIDER` finds its AI default on the machine (`backend/ai/detect`: the shell's `ANTHROPIC_API_KEY`, then `OPENAI_API_KEY`, then an Ollama with a model that calls tools, then LM Studio; `none` is none). It runs the standalone `foundry` image (Foundry's backend in one process: its API, a directory of the one owner's workspaces, projects and databases, and its workers; built from `backend/`), the ontology agent, SeaweedFS, MySQL and the public helix-db image. That HelixDB keeps no tenants apart: every ontology's loads share one database, so one ontology's Other data shows labels another's loads wrote. The site's `Dockerfile` builds its image.
- **Local build** (`NEXT_PUBLIC_FOUNDRY_MODE=local`, fixed at `next build`; `src/shared/deployment.ts`): a copy someone runs on their own machine. It has one owner and no sign-in, members, billing or sign-out. `/papi` (`src/server/local.ts`) answers only the Host of `FOUNDRY_ORIGIN`, which must be a loopback origin, and forwards as the owner with `FOUNDRY_LOCAL_TOKEN`, else the token in the file `FOUNDRY_LOCAL_TOKEN_FILE` names (read once it reads; shared with the API, 32+ bytes; the CSRF secret is derived from it) under the same allowlist, origin and CSRF checks. The API refusing the token is shown as a setup error, never a sign-in. Anything the hosted site shows about members, the plan or the Helix dashboard is behind `LOCAL`, as are People enrichment's settings (locally the API reads the setting as unavailable, so Edit offers no Enrich people). A local build offers no API source (`connectorKindsQuery` drops the `events` kind, and the palette has no New API source): their senders reach Foundry through the Helix MCP, which a local install doesn't run, and the local API refuses their send tokens.
- Refresh: Foundry access tokens live 300 s and WorkOS refresh tokens are single use. AuthKit refreshes 30 s before expiry, and a failed refresh while the token is still valid keeps the session. Once the token has run out, a second refresh of the same cookie fails and ends the session, so: every `/papi` answer says how long the token has left (`x-foundry-session-expires-in`, `src/shared/session-contract.ts`), and once that is under 10 s, or not known yet, `api.ts` sends its calls one at a time under a Web Lock shared by the origin's tabs until one reports a fresh token. That holds across server instances. On one instance, parallel calls also share one refresh per session cookie (`src/server/single-flight.ts`), and a rotated session is reused for 30 s by requests still carrying the old cookie.
- Onboarding: a workspace with no ontology shows nothing but the new-ontology wizard (`main.tsx`'s `WorkspaceRoutes`, `onboarding` on `useWorkspace()`). The sidebar keeps only the workspace switcher and the account menu (no nav, no search, no palette). Every other path redirects to `/ontology/new`, except an ontology's own pages (the one just created opens before the list has it) and `/settings/*` (the plan a database connection needs). The Helix MCP's connector links (`/data?add=<kind>`) open their form over the wizard. To test the full app in the mock, sign in as `ada@example.com`; a new email lands in onboarding.
- Workspace switching is client-side (`src/web/workspaces.ts`): a Foundry session works on every workspace the user belongs to. When sessions become workspace-scoped, the token swap goes in `chooseWorkspace`.
- Links into the app may name their workspace with `?workspace=<id>`: `SignedIn` opens and remembers it when the user belongs to it, says so when not, and drops the parameter. `/data?add=<kind>` opens that kind's form in the Add data modal (`?add=1` the picker). The Helix MCP's `helix_foundry_connector_link` sends users to `/data?add=<kind>&workspace=<id>`, so connector credentials are entered here, never through an agent.
- Sign-out returns to `/login`. WorkOS must list `https://<host>/login/callback` as a redirect URI and `https://<host>/login` as a logout redirect for the Foundry application.
- Password, SSO and email-verification sign-in are not offered: the callback sends those cases to `/login?error=sso|verify`.
- Foundry Pro and Max (`src/web/areas/workspace/plan.ts`, which holds the prices: Pro $100 and Max $500 a month; the WFE returns none): one Autumn group, so a workspace holds Free, Pro or Max, and Max grants everything Pro grants. Autumn is the system of record and the WFE reads it live, so the plan query is cached for a minute. Every stamp's plans offer every connector kind (paid plans sync more often); the WFE refuses a kind a plan leaves out (create, test, update and sync) with FAILED_PRECONDITION and reason `FOUNDRY_PRO_REQUIRED`, which the mock keeps for PostgreSQL, MySQL and S3 on Free. The Data area renders `<ProGate feature="PostgreSQL connections" />` (`areas/workspace/pro-gate.tsx`) for a kind with `available: false` (the picker, and a Pro connection's page after the workspace left Pro) and in place of a form error for which `isProRequired(error)` is true. It links owners and admins to `/settings/billing`, and the billing page refreshes the connector kinds once the plan bought shows. A Max workspace passes every Pro gate, so it never sees one. The plan's tier shows on Plan & billing and the account menu.
- Billing: checkout (`CreateFoundryProCheckout`) sends a new `clientToken` per click and always the `tier` (`FOUNDRY_TIER_PRO` or `FOUNDRY_TIER_MAX`; unset is Pro). From Free, the upgrade dialog picks Pro or Max and takes a promotion code; a paid workspace switches to the other tier from its card, behind a confirm dialog, by checking that tier out (asking for the tier held attaches nothing). Cancel and resume act on whichever tier is held. After an answer that may have charged (`checkoutFailure` is `unsure`) the page reads the plan before offering checkout again, and Autumn refuses a second attach of a held plan. Stripe Checkout returns to `/settings/billing` (the WFE's `billing.autumn.foundry.return_url`), and that page keeps reading the plan for a while after a checkout this tab started, until the tier it bought shows. The mock's checkout and billing portal are `/mock/checkout` and `/mock/billing-portal`; `POST /__mock/config {"checkoutCardOnFile": true}` charges without a page.
- `/` is Ask (`main.tsx` redirects it to `/ask`, keeping the link's query), on the ontology last opened, else the newest; a workspace without an ontology goes to the wizard. Ask is the sidebar's first section and is current on `/`, with its threads under the sections. There is no Home page.
- Mock users: `alan@example.com` is a plain member of Acme, for what non-managers see; `POST /__mock/config {"alanRole": "WORKSPACE_ROLE_ADMIN"}` makes him an admin until the next reset, for what admins (not owners) see. Any other new email starts with no workspace, named from the email unless the mock sign-in page's Name is filled in.
- Members are read-only here and invitations are create-only. Role changes, removal and pending-invitation management stay in the Helix dashboard (`NEXT_PUBLIC_HELIX_DASHBOARD_URL`, set per stamp in `next.config.ts`), where invitations also land.
- The PostgreSQL and MySQL guides list the stamp's outbound addresses from `NEXT_PUBLIC_HELIX_EGRESS_IPS` (set per Vercel environment: the stamp's NAT egress IPs); without it they only say to allow Helix's outbound address.
- API sources over HTTP: `NEXT_PUBLIC_HELIX_EVENTS_URL` (per stamp in `next.config.ts`: `https://ingest.helix-db.com` on prod, `https://ingest.dev.helix-db.com` on dev and in the mock, empty in local mode) is where Foundry's `foundry-events` role takes `POST /v1/sources/{id}/pieces` with a send token as the bearer. Empty, every mention of HTTP is hidden: the send panel's "Send over HTTP" (`eventSourceCurl()`, which reads the token from `HELIX_EVENT_TOKEN`, and `eventSourcePiecesExample()`), the prompts' HTTP section and `send_url` line, and the "app or agent" copy of the picker, palette, form, page and token. The mock doesn't serve the endpoint, and the site never calls it.
- The mock has one Foundry plan per workspace, in `mock/routes/billing.ts`: Acme starts on Pro, a new workspace on Free, and checkout moves it to the tier asked for. A switch between Pro and Max charges the card on file at once (no checkout page) and reads the old tier once, as a card-on-file purchase reads Free once. The Data routes' Pro gate reads it (`isFoundryPro`, true on Pro and Max); unit tests set it with `setFoundryPlan`. To test an upgrade end to end, start from a new workspace (`signInToNewWorkspace` in `tests/e2e/support/mock.ts`); a switch starts from Acme.
- Amazon S3 (`areas/data/connection-s3.tsx`, a Pro kind): files in one folder of a bucket become tables (the WFE lays keys out into tables; the user picks tables by name, `tables` empty meaning every one). Access is an IAM role or an access key. A role is offered only when the kind's `s3` setup (`principalArn`, the workspace's `externalId`) is in the connector kinds (an edit keeps a stored role, which without the setup can be renamed but not tested); the role panel shows the external ID and the trust and permissions policies to paste, written by `s3TrustPolicy` and `s3PermissionsPolicy` in `model.ts` exactly as the backend's S3 plan has them. A key's secret is write-only, and an edit that leaves it blank keeps the stored one; a role stores no secret. A test copies the region it detected into the form, and its tables carry `format`, `fileCount`, `bytes` (int64 strings, shown in binary units by `formatBytes`), up to 5 `preview` rows and a `problem` (the sync fails until it is fixed); Connect is disabled while the chosen tables' bytes are over the discovery's `maxBytes`. Changing the bucket clears an AWS region, which the next test detects again.
- Data (`areas/data`): every Data page sits beside the Data explorer (`explorer.tsx`), the workspace's data as a tree, as in an IDE: at its root a folder per connector kind that has a connection, the workspace's own folders of connections, and `documents/` (`documents-tree.tsx`) with a folder per document set holding its documents (`tree.tsx`). It is the Data section's panel beside the sidebar (`panel.data` in `shell.ts`, `<aside aria-label="Data explorer">`), outside the page's routes, so it reads only the URL and the query cache, and calls `onNavigate` on every link it follows (the phone drawer closes). It is a `role="tree"` (`useTreeItem` in `arrange.tsx`; `explorerRows`, `rowKeyAction`, `selectionOf` and `selectedRow` in `layout.ts`): one Tab stop (the row last focused, else the page's, else the first; only that row's buttons are in the Tab order), the arrow keys, Home and End move between rows and open and close folders, Enter opens a row and F2 renames it. The row of the page open (a connection's page or one of its tables', a document's) has `aria-current="page"`, and the folders holding it open once each time the URL changes. Closed folders are remembered per browser (`foundry.data.closed`: `kind:<kind>`, `folder:<id>`, `documents`, `set:<id>`); the filter opens what it finds and lists the tables it matched under their connection (a folder's or set's name keeps all it holds). A connection or document opens with a click (its link covers the row), a folder opens and closes. A connection's sync status is a dot, said in its row's name; what a row holds is its name's tooltip; Sync, and a set's Upload, Describe and Delete, show while the row is hovered or focused. Owners and admins rename a folder, a connection, a set or a document in place (`InlineName`, `inline-name.tsx`: helix-foundry's suggested-ontology rename, Enter or leaving the field saves, Escape cancels, Enter and Escape give the focus back to the row), sync a connection, and create, describe (a dialog: the agent reads the description) and delete an empty set. `/data` (`overview.tsx`) is an overview: the totals, the connections in a DataGrid (a row opens it), and the document sets with what they hold and which ontologies read them, with Add data (`?add=1`, `?add=<kind>`) and Upload documents. The generate form groups connectors by kind (`kindFolders()`, `setFolders()` in `model.ts`, not the layout): a kind with several nests them under one tri-state choice (`picked()`), a lone one shows as itself.
- The Data layout (`areas/data/layout.ts`, pure, in `test:coverage`): how the tree is arranged, shared by the workspace in one JSON object the WFE stores without reading (`GET/PUT .../foundry/data-layout`, at most 64 KiB of compact JSON, `{layout, revision}`). Version 1 is `{v: 1, names, folders: [{id, name}], order}` over the containers `root`, `kind:<kind>`, `folder:<id>`, `documents` and `set:<setId>`: `order` lists children (root's and documents' by container key, others by id), unlisted ones follow in the default order (kinds in the WFE's order, then custom folders, then documents/; everything else as created), so new ones go last. A connector sits in the custom folder whose order lists it, else its kind's; custom folders are root-level and hold connectors only, up to 50, names unique among root folders. `names` renames a kind's folder or documents/. `parseLayout` reads `{}` as empty and any other `v` as unknown: the tree then shows its usual order with a note and nothing moves. Every change is a `LayoutChange` that `applyChange` makes on any layout and prunes ids the workspace no longer has. `use-tree.ts` shows changes at once and saves them one PUT at a time; on FAILED_PRECONDITION it rereads the layout and lists and makes the change again once, then undoes it with a toast. It never writes while the connector, set, document or layout list is loading or failed. Owners and admins drag a row by its grip (`arrange.tsx`, `@dnd-kit/core` and `sortable`; a copy follows the pointer) within its list, a connection into a custom folder (its head: last; a row: before or after it by the pointer's half) or back to its kind's; clicking the grip, or Enter on it, opens its menu: Move up, Move down, Move to… for a connection, another set for a document (the WFE's move). New folder is in the explorer's head; a custom folder's menu deletes it, sending its connections back to their kinds' folders. The filter turns grips off; members see the order only.
- Data in the mock (`mock/routes/data.ts`, `data-sources.ts`): Acme starts with a synced Stripe account and PostgreSQL database. A key containing "bad" is rejected, a Stripe `rk_` key cannot read payouts, balance transactions or disputes, a PostHog key containing "multi" sees two projects, a GitHub token containing "nopr" cannot read pull requests or reviews, a repository named `*/missing` is one the token can't read, a Cal.com key containing "solo" has no teams (teams and team_memberships are unavailable), one containing "member" gets the Test warning that it is not a team admin, a Granola key containing "personal" cannot read spaces, the password "wrong" fails, private hosts are refused, and a PostHog sync over 90 event days fails. Syncs run about 2.5 s. With `MOCK_DOCUMENT_FIXTURES` (`pnpm dev:mock`), Acme's General set holds a read CSV and JSON file. A new table file reads for 1.5 s (`{"documentReadMs": n}`), and one that isn't what its type says fails its read. Every S3 bucket holds the plan's fixture folder, laid out by a port of the backend's layout (`data-files.ts`): tables api, customers, events, orders and products in eu-west-2, with notes.xlsx and an archived file it can't read. An S3 role ARN containing "untrusted" can't be assumed and one containing "open" doesn't require the external ID; the buckets missing-bucket, denied-bucket and empty-bucket fail as their names say, and bad-records has a malformed events sample, so its syncs fail. `{"s3RoleAccess": false}` takes the role setup away. There is no S3 seed. Syncs run about 2.5 s. The Data layout (`mock/routes/data-layout.ts`) starts empty at revision 0; a stale revision is FAILED_PRECONDITION, and `{"dataLayoutConflicts": n}` lets another writer come first on the next n PUTs.
- API sources (connector kind `events`; the WFE, its protos and the MCP call them event sources): people and their agents send them pieces of data, JSON objects with an id, through the Helix MCP; the site makes them and their send tokens and reads their sends, and never sends pieces itself (no WFE route does). A source is made, edited (name and description; its fields are learned from pieces, keep their first JSON type and are never sent) and deleted through the connector routes with `config.events`, and has one synced table, `events`, keyed by piece id. Its send tokens (`.../connectors/{connectorId}/tokens`, `hx_ev_` and 64 hex digits, shown once at create, at most 10 live) and recent sends (`.../event-batches`, with `pendingPieces` and `capacity`) have routes of their own. A source may have a text field (`config.events.textField`, the top-level field holding each piece's text), locked as a string once chosen; an update sends `description` and `textField` only to change them (left out, each stays; `""` clears the text field), and a text-field change queues one full sync and is refused while a sync of the source is live. A load's `enrichment` step reads `preparing`, `queued` (parked for a lookup slot), `running` (with **Stop looking up**), then `done`, `partial` with `stoppedBy`, `off`, `failed` or `cancelled`; its counts are int64 strings, `people = skipped + carried + toLookUp`, `carried` counts every earlier result reused (not found included), so "found before" is the applied profiles less this load's `found`, except for a step that published after its load stopped waiting for it: the load applied only profiles found before, and `found` is for the next load. The WFE doesn't flag that step, so `stoppedWaiting` tells it from a step still queued or running while its load job is past its first step or has ended (it reads "Still looking up after the load stopped waiting", without its counts), or from one that published after the load ended; one that published while the load went on reads as on time until the contract says so. A stopped step reads "Stopped after N", not "Stopped by Ada Lovelace after N": `FoundryLoad.enrichment` names no user (the backend keeps who in `stop_requested` but doesn't send it), so naming them waits for a contract field. A value a profile stated carries the "People enrichment" chip, linking the load. Ask cites a profile without its id (contract 3.12.0: an empty `row_key` for `foundry_enrichment`, and only for it), as "A People enrichment profile" opening the load.
- People enrichment in the mock (`mock/routes/enrichment.ts`, `loads.ts`): the operators' flag is on unless `POST /__mock/config {"enrichmentFlag": false}`, which reads DISABLED, refuses turning it on or a new cap (off still works), ends steps `partial(flag)`, refuses enrichment edits in Revise and keeps the agent from proposing it. The planner counts as the backend's does, the agent's measure of an item's clues (`measureClues`) as the engine's Clues does, without the planner's filters (so the Sales graph measures 12 of 14 usable while a load looks up 9), and `fakeEnrich` decides by the clue's text ("bad" not found, "low" scores 72, "dup" shares a profile, "other" fails the name check, "timeout" is uncertain, free-mail and role addresses are skipped). A load of the Sales graph looks up 9 of its 14 people, 2 a batch: Ada, Grace, Alan and Katherine are found, 4 are held and Bea isn't found (160 credits); the next load carries all 9 and doesn't park. `POST /__mock/config {"enrichmentStepMs": 300, "enrichmentOutcome": "cap"}` sets a batch's time (and the wait for a slot) and how the lookups stop (`cap`, `provider_credits`, `provider`, `time` or `busy`). A step that ends wakes its parked job, which stays queued at `provisioning` a step until it is picked up again, as the WFE's wake leaves it. Turning consent off cancels live steps and purges each ontology with a load that applied profiles, current or not (a load still writing counts), as the WFE does: once no job is live, a current load holding them is loaded again without them, the others holding them are deleted once a clean load is current, and none of them can be made current.

## Review decisions

- Reviews use their `review_key` for settle calls. Send only a `FoundryReviewChoice`; the backend derives the decision identity from the current load. The list returns flat camelCase decisions, 100 a page by last decision id, with no filter, so pages read it all; settling never waits for it. Only the current load can be settled; decisions and their removal apply from the next load ("Reload to apply"). A load reads the decisions saved when it was created (the backend snapshots them, and so does the mock, catch-up extracts included), so a decision saved before the shown load started was read by it: if its review is still there, what it chose isn't in that load, and the page says so instead of asking to reload.
- `reviews/model.ts` `settleable()` reads a review once, from its record and the entities it concerns (`FOUNDRY_CONCERNS`, read with the review): a `resolve` review (identity `type`, `doc_id`, `norm_name`), a `prop` review (`type`, `entity_key`, `prop`, `values`, and the entity's stored value), or `stale` when the identity the backend reads, or the entity, is missing (a load from before decisions: "Load again to settle this review"). Candidates are stored identities (a key's tagged encoding, such as `scus_…`), shown by the concerned entity's name and linked to its page.
- A property only a table row can hold through a conflict, so a `prop_conflict` whose entity has a stored value is a row conflict: its `values` list only the quotes that disagree with the table. The page says the table's value is kept and offers the documents' values as "Replace the table’s value with", warning that a decision holds in every later load, even after the table changes. It never offers to pin the table's value.
- An adjudicated resolution has an informational `FoundryReview` with reason `adjudicated`, its type, document, normalized name, chosen entity key and confidence; its only candidate is that entity. Treat it as a resolve review; "Undo link" saves `resolve: {notInData: true}`. Mentions marked `adjudicated` link to the document's review tab. Auto-adjudication stays off; the mock's opt-in `documentAdjudicated` fixture seeds a variant and its review for undo tests.
- Property-conflict `values` are the engine's JSON-encoded `PropQuote` records, including each value, document, span and quote. Parse them before offering a value; never send the whole quote as the value.
- The mock's settle route checks what the backend checks, with its codes (`mock/review-decisions.ts`): no current load and a review without identity, or whose type or prop the loaded version lacks, are `FAILED_PRECONDITION`; a chosen entity not in the load and a value the engine refuses are `INVALID_ARGUMENT`. A value is stored as the engine keeps it: strings trimmed (a blank one refused), dates `YYYY`, `YYYY-MM` or `YYYY-MM-DD`, datetimes in UTC (a UTC year outside 0000 to 9999 refused), `null` removes the value. Making a version current drops the decisions it doesn't take (an agent draft with types only), as the backend's set-current does; a newer draft alone changes nothing. Version 3's route lets documents state a customer's `currency`, which the customers table sets: "<customer> is billed in GBP." in a document makes a row conflict.

## Backend

`backend/` is the Go module `github.com/helixdb/helix-foundry/backend` ([backend/README.md](backend/README.md)): Foundry's API, its workers, its MySQL store and migrations. Its checks run in `backend/`: `go build ./...`, `go vet ./...`, `gofmt -l .` (prints nothing), `golangci-lint run ./...` (v1.62.2), and `go test ./...` with the test databases up (`docker compose -f compose.test.yaml up -d --wait`). After a `.proto` change, `buf generate && buf generate --template buf.internal.gen.yaml` regenerates `pb/gen`, which is committed. `.github/workflows/backend-check.yml` runs the checks and the regeneration on every change; `.github/workflows/backend.yml` runs the tests and builds the image (`docker build backend`) on changes to `backend/`.

- Hosted Helix imports this module and runs it inside its own server. REST paths, verbs and JSON shapes, SQL and transactions, migration versions, config keys, environment variable names, metric names and worker schedules are shared with that deployment: change them on purpose, never as a side effect.
- The module imports only its own packages, the standard library and public modules. What differs when hosted (sign-in and roles, workspaces, Helix databases, plans) comes in through the module's interfaces.
- Migrations are embedded from `store/migrations` (goose). Hosted runs them in one sequence with its own, so a new migration takes a version later than every existing one, and a shipped migration is never edited or renumbered.
