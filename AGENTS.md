# Helix Foundry: agent guide

The Helix Foundry site, in two builds: the hosted site, foundry.helix-db.com (branch `main`) and dev.foundry.helix-db.com (branch `dev`) on Vercel, and the local build that `local/` runs on one machine. A Next.js 16 app that serves three things:

- the Foundry UI: a single-page app (react-router 7, TanStack Query), mounted client-only;
- sign-in: helix-website's WFE-brokered WorkOS flow, run as the Foundry AuthKit application;
- `/papi`: a same-origin BFF that forwards an explicit allowlist of WFE routes with the session's bearer token.

Foundry's API is `backend/` (Backend, below): `helix.foundry.v1`, every route under `/v1/foundry` and `/v1/workspaces/{workspaceId}/foundry`. Hosted, the Helix WFE serves those routes beside its own, which the site also calls (whoami, workspaces, members, projects, tenants, billing). Their REST contract is vendored in two parts, Foundry's in `contract/foundry.swagger.json` and the WFE's own in `contract/wfe.swagger.json`, with the ontology agent's Read and Ask JSON Schemas, whose JSON Foundry carries as strings, in `contract/ontology_agent/` with their `VERSION`. `pnpm contract:sync` copies Foundry's contract and the schemas from `backend/`, and the WFE's from `WFE_REPO`, a checkout of hosted Helix's backend, which only Helix's maintainers have.

Next.js 16 differs from older versions. Read the matching guide in `node_modules/next/dist/docs/` before using an API you have not used here.

## Rules

- **The allowlist.** The browser reaches the WFE only through routes listed in `src/server/papi-allowlist.ts`: one entry per method and path, written exactly as in the swagger, with `{param}` matching one path segment. No wildcards, no prefixes. Add only routes the UI calls. Never add sign-in, SSO management, role changes or member removal; the one exception is connecting a directory (its status, the Admin Portal link and a sync now, below), whose roles from groups stay in the dashboard. `tests/unit/papi-allowlist.test.ts` fails unless every entry is in the contract and served by the mock.
- **WFE types** live in `src/shared/wfe.ts` only, written from the swagger, under a heading per area. grpc-gateway JSON is camelCase, enums are names, int64 are strings, and default values may be missing.
- **Agent JSON** (Read results, Ask events and results) is the engine's, typed from `contract/ontology_agent/` in `src/shared/foundry-read.ts` and `wfe.ts` "Ontology: questions", and parsed without trust. The mock emits exactly those shapes, and `tests/unit/agent-contract.test.ts` validates every mock answer, every fixture and the reads the SPA sends against the schemas (`mock/agent-contract.ts`, ajv), so a contract change fails CI.
- **Calls** go through `api()` in `src/web/api.ts` with WFE paths (`api("/v1/whoami")`). It adds the CSRF header on unsafe methods and sends a signed-out user to sign-in.
- **Look.** Everything uses the kit, shell, tokens and copy tone (`src/web/kit`, `src/web/shell`, `src/web/workspace.css`). Build a new screen from the kit and an existing area's CSS rather than inventing styles, with colors as tokens. Do not edit the kit to suit one screen.
- **Colors** are `--hf-*` tokens in `src/web/workspace.css` only: the light set on `:root`, the dark set in two identical blocks (`@media (prefers-color-scheme: dark)` under `:root:not([data-theme="light"])`, and `:root[data-theme="dark"]`). A new color gets a value in all three, or is listed in `SAME_IN_BOTH`. No other CSS in `src/web` has a color literal; `tests/unit/theme-css.test.ts` checks that, and the dark theme's contrast (4.5:1 text, 3:1 icons and marks).
- **Cookies** are Foundry's own and host-only: `__Host-foundry-session` (`WORKOS_COOKIE_NAME`), `__Host-foundry-csrf`, `__Host-foundry-login-<flow>`, `__Host-foundry-reset`. On loopback http (mock, e2e) they drop the `__Host-` prefix. Never set a cookie domain.
- **Secrets** never go in the repo. `.env.example` names the variables. The values in `mock/env.ts` are mock-only fixtures.

## Adding an area

An area (Workspace, Data, Ontology) owns its folder (step 1) and adds to four shared files, each in a section of its own (steps 2 to 5):

1. `src/web/areas/<area>/`: `index.tsx` (route components; Data, Ontology and Dashboards export a `*Routes` table for their URL prefix, and Ontology also `ExploreRoutes` and `AskRoutes` for `/explore` and `/ask`), `paths.ts` (URL helpers, merged into `src/web/paths.ts`), `shell.ts` (sidebar children, a section's panel and command-palette sources), and its CSS.
2. `src/web/main.tsx`: the area's routes, if it adds a new prefix.
3. `src/server/papi-allowlist.ts`: one line per WFE route the area calls, in the area's section.
4. `src/shared/wfe.ts`: the payload types, under the area's heading.
5. `mock/routes/<area>.ts`: the same routes with in-memory state, spread into `mock/routes/index.ts`. Use `membership()` from `mock/state.ts` for workspace-scoped routes and `onReset()` for the area's state.

Then add the area's main flow to `tests/e2e/` and its logic to `tests/unit/`.

## Things to know

- Names and Records: wherever an entity shows (the Explorer's canvas, tooltips, inspector and search, Records, an entity's page, a document's view) it reads by the version of the load the page reads (`explore/naming.ts`, `useNaming(versionId)`): the first non-empty `names` prop of its type, else its key props joined, else its stored `name`, else a short id; a label the version doesn't know, or no current version, keeps the raw label and the explorer's own caption. `<prop>__nn` (normalized names), an entity's `entity_key` and `norm_name`, a fact's `fact_key`, anything's `foundry_load` and Foundry's other stamps (`foundry_*`, such as `foundry_tx`) on all but Foundry's own labels never show in property lists; those stamps (`isFoundryStamp`) also never match the Explorer's search or take its `contains` scan's keys. Records (`/explore/{id}/records`, `areas/records`) is the Explorer's table view: its types are listed in the Explorer's panel (above the table while the panel isn't on screen); every query in `records/model.ts`, each bounded (a page is `range` over one type, one row more than a page, at most 10,000 rows deep; searches and filters count up to 1,000). A datetime prop is Helix's typed DateTime (UTC milliseconds, read back as `YYYY-MM-DDTHH:MM:SS.mmmZ`), which equals only a DateTime: a filter, a datetime key's search and a typed read's search send the instant through `helixDateTime` (`src/shared/datetime.ts`: chrono's RFC 3339, in UTC, truncated to the millisecond) as a `date_time` parameter (`parameter_types`) or, through grants, as that text for the engine to type; text that isn't an instant is refused, and no datetime is ever searched with `contains`. The engine's own JSON writes the same instant with no fraction or three digits (`…:00Z`); both are RFC 3339, so a comparison (a decision's value, `holdsDecided`) reads both through `helixDateTime`.
- **Running Foundry locally**: `local/` (compose, README, `.env.example` of optional overrides) runs the local build, with nothing to set up: `docker compose up -d --wait` from the root (its `compose.yaml` includes `local/compose.yaml`: one project, `helix-foundry`, the same volumes from either place, and Compose reads `local/.env` for that file from either) or from `local/`. Its first service, `init-secrets` (`foundry init-secrets` in the foundry image, offline), writes the secrets the `secrets` volume lacks, once: an old install's `FOUNDRY_*` from its `local/.env` (setup.sh's, before 0.1.1), else random ones; every other service waits for it and reads its own from the volume (the site `FOUNDRY_LOCAL_TOKEN_FILE`, MySQL `MYSQL_PASSWORD_FILE`, the store its file, foundry `local.secrets_dir`). The connector key there seals every stored credential and is never made again. foundry makes the owner's first workspace, My workspace, until the install has had one, and with no `FOUNDRY_AI_PROVIDER` finds its AI default on the machine (`backend/ai/detect`: the shell's `ANTHROPIC_API_KEY`, then `OPENAI_API_KEY`, then an Ollama with a model that calls tools, then LM Studio; `none` is none). It runs the standalone `foundry` image (Foundry's backend in one process: its API, a directory of the one owner's workspaces, projects and databases, and its workers; built from `backend/`), the ontology agent, SeaweedFS, MySQL and the public helix-db image, every image pinned by tag and multi-arch digest (a release bump changes both, as the comment above `x-images` says). That HelixDB keeps no tenants apart: every ontology's loads share one database. foundry also serves MCP and HTTP Ask on the REST listener the site calls, which `local/compose.yaml` publishes on the host's loopback (8081, or `FOUNDRY_MCP_PORT`), with the owner's site token as the bearer, and the routes of Founder’s helper (below) with tokens of their own; MCP and HTTP Ask answer only for loopback, `host.docker.internal` and the host of `local.site_origin` (`integrationHosts`), while the site's routes are limited only by the token, its probes stay on the health listener, and the links agents get start from `local.site_origin` (compose's `HELIX_LOCAL__SITE_ORIGIN`, the site's `FOUNDRY_ORIGIN`). At every start foundry queues a full reload of every current load a release owes one (`local.RebuildOwedLoads`): a directory migration of that release adds a row to `foundry_local_rebuilds` at the time it ran (00005: the typed DateTime release), and each live ontology whose current load is older is reloaded (`store.RebuildFoundryLoads`), at start and then every minute (`local.Rebuilds`), until none is queued, reloading or held back by a live job (one whose reloads failed three times is given up on, and logged). The site's `Dockerfile` builds its image.
- **Local build** (`NEXT_PUBLIC_FOUNDRY_MODE=local`, fixed at `next build`; `src/shared/deployment.ts`): a copy someone runs on their own machine. It has one owner and no sign-in, members, billing or sign-out. `/papi` (`src/server/local.ts`) answers only the Host of `FOUNDRY_ORIGIN`, which must be a loopback origin, and forwards as the owner with `FOUNDRY_LOCAL_TOKEN`, else the token in the file `FOUNDRY_LOCAL_TOKEN_FILE` names (read once it reads; shared with the API, 32+ bytes; the CSRF secret is derived from it) under the same allowlist, origin and CSRF checks. The API refusing the token is shown as a setup error, never a sign-in. Anything the hosted site shows about members, the plan or the Helix dashboard is behind `LOCAL`, as are People enrichment's settings (locally the API reads the setting as unavailable, so Edit offers no Enrich people). A local build offers no API source (`connectorKindsQuery` drops the `events` kind, and the palette has no New API source): local MCP supports the connector/document workflow; API source operations and their send tokens remain disabled.
- Refresh: Foundry access tokens live 300 s and WorkOS refresh tokens are single use. AuthKit refreshes 30 s before expiry, and a failed refresh while the token is still valid keeps the session. Once the token has run out, a second refresh of the same cookie fails and ends the session, so: every `/papi` answer says how long the token has left (`x-foundry-session-expires-in`, `src/shared/session-contract.ts`), and once that is under 10 s, or not known yet, `api.ts` sends its calls one at a time under a Web Lock shared by the origin's tabs until one reports a fresh token. That holds across server instances. On one instance, parallel calls also share one refresh per session cookie (`src/server/single-flight.ts`), and a rotated session is reused for 30 s by requests still carrying the old cookie.
- Onboarding: a workspace with no ontology shows nothing but the new-ontology wizard (`main.tsx`'s `WorkspaceRoutes`, `onboarding` on `useWorkspace()`). The sidebar keeps only the workspace switcher and the account menu (no nav, no search, no palette). Every other path redirects to `/ontology/new`, except an ontology's own pages (the one just created opens before the list has it) and `/settings/*` (the plan a database connection needs). It opens on Get started (`choosing` in `new-ontology.tsx`): the sample, then one section whose toggle (`Segmented`) starts on Set up with your agent (`AgentSetup`: Copy prompt), its other side Use my own data (Continue opens the wizard); a local build starts on Use my own data, and its agent setup goes through the install's own MCP (`local-onboarding-prompt.ts`). The Helix MCP's connector links (`/data?add=<kind>`) open their form over the wizard. To test the full app in the mock, sign in as `ada@example.com`; a new email lands in onboarding.
- Workspace switching is client-side (`src/web/workspaces.ts`): a Foundry session works on every workspace the user belongs to. When sessions become workspace-scoped, the token swap goes in `chooseWorkspace`.
- Links into the app may name their workspace with `?workspace=<id>`: `SignedIn` opens and remembers it when the user belongs to it, says so when not, and drops the parameter. `/data?add=<kind>` opens that kind's form in the Add data modal (`?add=1` the picker). The Helix MCP's `helix_foundry_connect` sends users to `/data?add=<kind>&workspace=<id>` for a kind's form, so connector credentials are entered here, never through an agent.
- Add data's picker (`areas/data/connect-data.tsx`): opened from the app (the Connectors page's button, the explorer's +, the palette) it pushes an entry carrying `PICKER_OPENED` (`areas/data/paths.ts`), so Back closes it and closing goes back to where it was opened; a link without it (an agent's, a reload) closes in place. A connect from it ends on `Connected` (Add another source, Open, which replaces the picker's entry) unless the caller takes `onConnected` to stay where it is. The open picker remounts on a new `add=` or `sign_in=`, closes on the backdrop only when the press began there, and keeps dropped files from the Data page's upload. Enter tests a connection until a test passes; settings changed after a test say to test again.
- Feedback (`src/web/feedback.ts`, `shell/feedback.tsx`): the sidebar's Feedback button (the rail's icon on a phone), on every page and while onboarding, sends a kind (Bug, Idea, Confusing, Other), the words and the page's path (never its query or hash) to the WFE's `POST /v1/feedback`, which stores it beside the MCP's `helix_feedback` and tells the team in Slack with a Linear issue (at most 20 an hour a person, shared with their agents). Request a connector (`areas/data/request-connector.tsx`, anyone in the workspace: the Connectors page's Connections section and under the picker's kinds) sends `FEEDBACK_CATEGORY_CONNECTOR_REQUEST` with "Connector: <name>" on its first line. A local build has no Helix to tell: both open GitHub's new-issue page for helixdb/helix-foundry, filled in. Analytics carries the kind only (`feedback_sent`, `connector_requested`), never the words. The mock keeps what it takes with the WFE's rules (`mock/routes/feedback.ts`; `GET /__mock/feedback`, `mock.feedback()` in the e2e).
- Sign-out returns to `/login`. WorkOS must list `https://<host>/login/callback` as a redirect URI and `https://<host>/login` as a logout redirect for the Foundry application, and `https://<host>/connect/callback` as a redirect URI for connecting a source by signing in (below); the stamp's Helix Foundry GitHub App has `https://<host>/connect/github` as its setup URL.
- Email and password (`src/web/password.tsx`, `src/server/password.ts`): the sign-in page's form under the providers, `/login/sign-up` (name, email, password), `/login/forgot` and `/login/reset` POST to `/auth/password/{sign-in,sign-up,forgot,reset}` (same origin), which call the WFE's password routes as the Foundry application; the password goes nowhere else. Their answers take the exchange's two detours below: `emailVerificationRequired` comes with a `sessionId`, sealed into a login cookie named by its hash, so `/login/verify` and `/auth/verify-email` take it as the callback's. A wrong email or password never says which. Forgot answers the same for an address without an account. WorkOS's email links to `/reset-password?token=` (the WFE's `auth.applications.foundry.password_reset_url`), a route that keeps the token in the `__Host-foundry-reset` cookie and opens `/login/reset`, so no URL, history entry or analytics beacon carries it. Two exchanges come back without tokens (`src/app/login/callback/route.ts`, `src/server/sign-in.ts`). WorkOS wants the code it emailed when it hasn't seen the address verified, which a GitHub or Microsoft account often isn't (`emailVerificationRequired`): the callback keeps the login cookie, sealed again with the address (`verifyEmail`), and opens `/login/verify?flow=<flow>` (`VerifyEmailPage` in `sign-in.tsx`). That page reads the address from `GET /auth/verify-email` and sends the code to `POST /auth/verify-email`, which calls the WFE's `VerifyEmail` under the kept login: a wrong code, or the WFE away, keeps it for another try; an ended one goes to `/login?error=verify`. The email's company requires its single sign-on (`ssoRequired`, from either): a new login starts with `AUTH_PROVIDER_SSO` and the email, in place of the first, once (the transaction's `sso`); a second refusal, or a domain without SSO, is `/login?error=sso`.
- The sign-in page opened cold (no `return_to`, which the app adds when it sends a signed-out user there from any page but `/`, and no `?error=`; signing out lands there too) shows a short pitch beside the card, under it on a phone (`Pitch` in `sign-in.tsx`, `GatePage`'s `aside`): a line, three points and a link to the landing page's Ask demo (helix-website's `#foundry-ask`, tagged `utm_source=foundry&utm_medium=login&utm_campaign=pitch`). The other gate screens have none.
- Foundry Pro and Max (`src/web/areas/workspace/plan.ts`, which holds the prices: Pro $100 and Max $500 a month; the WFE returns none): one Autumn group, so a workspace holds Free, Pro or Max, and Max grants everything Pro grants. Autumn is the system of record and the WFE reads it live, so the plan query is cached for a minute. Every stamp's plans offer every connector kind (paid plans sync more often); the WFE refuses a kind a plan leaves out (create, test, update and sync) with FAILED_PRECONDITION and reason `FOUNDRY_PRO_REQUIRED`, which the mock keeps for PostgreSQL, MySQL and S3 on Free. The Data area renders `<ProGate feature="PostgreSQL connections" />` (`areas/workspace/pro-gate.tsx`) for a kind with `available: false` (the picker, and a Pro connection's page after the workspace left Pro) and in place of a form error for which `isProRequired(error)` is true. It links owners and admins to `/settings/billing`, and the billing page refreshes the connector kinds once the plan bought shows. A Max workspace passes every Pro gate, so it never sees one. The plan's tier shows on Plan & billing and the account menu.
- Billing: checkout (`CreateFoundryProCheckout`) sends a new `clientToken` per click and always the `tier` (`FOUNDRY_TIER_PRO` or `FOUNDRY_TIER_MAX`; unset is Pro). From Free, the upgrade dialog picks Pro or Max and takes a promotion code; a paid workspace switches to the other tier from its card, behind a confirm dialog, by checking that tier out (asking for the tier held attaches nothing). Cancel and resume act on whichever tier is held. After an answer that may have charged (`checkoutFailure` is `unsure`) the page reads the plan before offering checkout again, and Autumn refuses a second attach of a held plan. Stripe Checkout returns to `/settings/billing` (the WFE's `billing.autumn.foundry.return_url`), and that page keeps reading the plan for a while after a checkout this tab started, until the tier it bought shows. The mock's checkout and billing portal are `/mock/checkout` and `/mock/billing-portal`; `POST /__mock/config {"checkoutCardOnFile": true}` charges without a page.
- `/` has no page of its own (`src/app/(app)/page.tsx`): on the hosted site a visitor without a session cookie goes to Foundry's landing page, helix-website's home (`https://www.helix-db.com/`, keeping the link's query), where its reminders and setup prompt now live, and `/index.md` goes to its Markdown (`https://www.helix-db.com/index.md`, `src/app/index.md`; not found in a local build). With a session cookie, and in every local build, `/` redirects to `/ask` keeping the link's query but its `via` (a session that has run out is the app's to send to sign-in). The SPA's own `/` is Ask too (`main.tsx` redirects it to `/ask`, keeping the link's query), on the ontology last opened, else the newest; a workspace without an ontology goes to the wizard. Ask is the sidebar's first section and is current on `/`, with its threads under the sections. There is no Home page.
- Reminders: helix-website's landing page takes a phone visitor's email for Foundry's door to remind them to try Foundry on a computer. Signing in here stops them: `login/callback` tells the door that address signed in (`after()`, `stopReminders` in `src/server/reminders.ts`, `POST /v1/reminders/stop` on `HELIX_INGEST_ORIGIN`, else `NEXT_PUBLIC_HELIX_EVENTS_URL`, with `FOUNDRY_REMINDERS_SECRET` as the bearer), asking again after 1 s and 4 s while the door is away or busy. Without the secret, and in a local build, it stops none.
- Mock sign-in (`mock/routes/auth.ts`, `mock/state.ts`): a new address containing `unverified` is one WorkOS hasn't seen verified, so its first sign-in asks for the code, which in the mock is always `424242`; an address at `sso.example` gets `ssoRequired` from any provider and signs in through the mock's single sign-on; no other domain has SSO. Ada's password is `correct-horse-battery`; a password sign-up makes an unverified user (so it asks for the code), a password under 10 characters is refused in WorkOS's words, and forgot keeps a reset token for a known address, which `GET /__mock/password-resets` lists and a reset uses once.

## Review decisions

- Reviews use their `review_key` for settle calls. Send only a `FoundryReviewChoice`; the backend derives the decision identity from the current load. The list returns flat camelCase decisions, 100 a page by last decision id, with no filter, so pages read it all; settling never waits for it. Only the current load can be settled. A name's decision applies to the current load at once, as an approval and a chosen value do (a resend job sends its documents again, the alias's too; `applied` says what became of it), except a name the load already links another way, or a load built before names could be applied in place: those apply from the next load ("Reload to apply"). A load reads the decisions saved when it was created (the backend snapshots them, and so does the mock, catch-up extracts included), so a name's decision saved before the shown load started was read by it: if its review is still there, what it chose isn't in that load, and the page says so instead of asking to reload.
- An approval of a held claim (a `release`) applies to the current load at once. The backend adds the decision to that load's own list and queues one resend job (`GraphJob.kind` `resend`) that sends the claim's document to the engine again, at no model cost; the document never leaves the load. From contract 4.17.0 the engine writes the claim from the review the load keeps (its statement at its place, its score, and the model, verifier and prompt its commit recorded) and asks no model, so the job sends no artifact, and an approval on a load built under other prompts or models is written too (through 4.16.0 the engine replayed the document's saved extraction, and one that no longer replayed was refused `not_replayed`). ## Backend

`backend/` is the Go module `github.com/helixdb/helix-foundry/backend` ([backend/README.md](backend/README.md)): Foundry's API, its workers, its MySQL store and migrations. Its checks run in `backend/`: `go build ./...`, `go vet ./...`, `gofmt -l .` (prints nothing), `golangci-lint run ./...` (v1.62.2), and `go test ./...` with the test databases up (`docker compose -f compose.test.yaml up -d --wait`). After a `.proto` change, `buf generate && buf generate --template buf.internal.gen.yaml` regenerates `pb/gen`, which is committed. `.github/workflows/backend-check.yml` runs the checks and the regeneration on every change; `.github/workflows/backend.yml` runs the tests and builds the image (`docker build backend`) on changes to `backend/`.

- `store.RebuildFoundryLoads(ctx, store, before)` queues a full refresh load (`QueueFoundryRebuild`) of every live ontology's current load created before `before`, whatever its refresh setting: the reload of loads an earlier engine wrote (the typed DateTime cutover). It is idempotent (a live rebuild is `UnderWay`, another live job `Busy`, a newer current load not owed); a live apply or delete gives way to it (the apply's refresh is owed again), its job's client token is `model.FoundryRebuildToken` (the graph worker doesn't compare it as apply drift), and after `store.MaxFoundryRebuilds` (3) rebuilds of one load ended without replacing it, it gives up on that load (`GaveUp`). It never rebuilds a sample's load (`Samples`: the current load's version was drafted from a sample; a manual edit of it is not one): the sample's data is fixed and its datetimes are to the minute, which Helix's own conversion types exactly, so a rebuild would write the same graph at a model cost. A rebuild of a sample an earlier run queued is withdrawn while it is still queued (cancelled, its never-written load deleted at once, no delete job), so re-running the command leaves only customers' rebuilds in the queue; one already started runs to its end. Re-run it until nothing is `Queued`, `UnderWay` or `Busy`. Hosted runs `foundry rebuild-loads --current-created-before=<RFC 3339>` against the configured database per stamp; a standalone install runs it at start (`local.RebuildOwedLoads`) and then every minute (`local.Rebuilds`) until nothing is left to queue or wait for, and only then marks its `foundry_local_rebuilds` row done.
- Hosted Helix imports this module and runs it inside its own server. REST paths, verbs and JSON shapes, SQL and transactions, migration versions, config keys, environment variable names, metric names and worker schedules are shared with that deployment: change them on purpose, never as a side effect.
- The module imports only its own packages, the standard library and public modules. What differs when hosted (sign-in and roles, workspaces, Helix databases, plans) comes in through the module's interfaces.
- `integration/` is the Foundry MCP's tools and HTTP Ask (`contract/foundry-integration.openapi.json`, `examples/ask_tool.py`), shared with hosted Helix; `local/integration.go` serves them on an install. `Service.Events` says the host has API sources: without it no tool, description or schema names them (`foundry_schema.go`), and a tool reads none of their methods, which an install doesn't serve. Every other method a tool calls must be in `local/methods.go` (`local/integration_test.go` checks).
- The landing page's reminders (helix-website's; `reminder/`, `api/reminders.go`, `store/foundry_reminders.go`, `services/foundry-events`, `workers/foundry-notify-worker`):
  - **Taking one:** the door's `POST /v1/reminders` and `/v1/reminders/stop` take the site's secret as their bearer. The door hashes the bearer and calls `FoundryEventsService.CreateFoundryReminder` and `StopFoundryReminders`, which compare the hash with `foundry.reminders.secret_sha256`; empty means off for new ones (those scheduled still send). So the door stays secretless. It refuses a bearer not of the secret's form (64 lowercase hex) before its room, counts each address's failed bearers as sends count failed tokens, and holds an address's places in flight as a send does; the bearer the backend last took skips those address checks for 10 minutes, as the site calls from addresses a cloud shares.
  - **The schedule:** one per address (`foundry_reminders`). The first goes at the next weekday 09:00 in the address's zone at least an hour away (`reminder.First`), then `gap_days` (7, 14, 28) apart, each on a weekday at 09:00 (`reminder.After`). Asking again while it runs changes nothing. One that ended starts again no sooner than `min_gap_days` after its last email; a stop while one is sent keeps its claim, so the send is still counted. At most `max_new_per_hour` start an hour, and `max_new_per_client_per_hour` (5) for one `client`, the site's key for a visitor.
  - **Sending:** the notify worker sends them through `ports.Mail` with no user (`Recipient{Email}`) on the topic `ports.TopicFoundryReminder` (`foundry-reminder`). The host must add that topic to its SES contact list, and give it a footer, before it ships.
- Migrations are embedded from `store/migrations` (goose). Hosted runs them in one sequence with its own, so a new migration takes a version later than every existing one, and a shipped migration is never edited or renumbered.
- Source grants (`backend/access`): `Register` runs every method through the access check, so a grantee (`SOURCE_GRANTEE`, a restricted member, or a user or key a host sends as one) reaches only what `access.RuleOf` admits, deny by default; `access.GranteeAdmits` tells a host which methods a refused caller may be sent to as a grantee. Giving a member or a team grants restricts them in the same transaction, and taking grants away never lifts it. A host implements `People.Member` (role, and whether the member reads databases outside Foundry), stamps a key's `service_credential_id`, and calls `DeleteFoundryAccessPrincipal` when it revokes a key and `RemoveFoundryAccessMember` when it removes a member. A new method needs a rule in `access/rules.go` (its tests fail until it has one). Founder for a restricted member: its six thread routes are `Workspace` (actions, the runtime and helpers stay `Deny`), and `agentUser` still takes users only, never a caller a host sends on as a grantee, so a restricted member reaches them as a user, narrowed by `granteeOf` and the turn's `Reach`. The worker reads `Reach` each attempt from `GetMyFoundryAccess` (`ReachGrants` when `grantee`; a failed read fails the turn, retryably, with no tools): under `ReachGrants` it offers only `GranteeTools` (reads, the dashboards it may read, `helix_foundry_ask` and its questions, `ask_person` without relaying a draft's questions), the sink allows and auto-runs nothing, the prompt adds `granteePrompt`, and an automation turn fails for good. `SendFoundryAgentMessage` keeps only the page context a grantee holds (its covered ontology and load, a pinned dashboard, never a new automation), and a thread is there for a grantee only while it holds every grant the thread ran under (`model.FoundryAgentThread.Granted`, `granted_targets`, `access.Grants.Holds`): nil for one made or run with the whole view, set at its creation by a grantee, cleared by an owner's or admin's send, and recorded by the worker each attempt and around each of a grantee's tool calls (`threadReach`, `reachAround`: a whole view's run clears it for good, a grantee's adds what they hold; a grantee's turn in a thread whose grants they lost fails for good, and a call during which their role or grants changed clears it and fails the turn before its result reaches anyone). The list fills its page past threads it leaves out (`ListFoundryAgentThreads`' `keep`). A host's `integration.SessionHost` must forward members on these routes as users, open the session for any member and call Foundry as that user, and give the session the member's MCP identity (`IsGrantee`, `FoundryGrants`).
