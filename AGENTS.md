# Helix Foundry: agent guide

The Helix Foundry site, in two builds: the hosted site, foundry.helix-db.com (branch `main`) and dev.foundry.helix-db.com (branch `dev`) on Vercel, and the local build that `local/` runs on one machine. A Next.js 16 app that serves three things:

- the Foundry UI: a single-page app (react-router 7, TanStack Query), mounted client-only;
- sign-in: helix-website's WFE-brokered WorkOS flow, run as the Foundry AuthKit application;
- `/papi`: a same-origin BFF that forwards an explicit allowlist of WFE routes with the session's bearer token.

Foundry's API is `backend/` (Backend, below): `helix.foundry.v1`, every route under `/v1/foundry` and `/v1/workspaces/{workspaceId}/foundry`. Hosted, the Helix WFE serves those routes beside its own, which the site also calls (whoami, workspaces, members, projects, tenants, billing). Their REST contract is vendored in two parts, Foundry's in `contract/foundry.swagger.json` and the WFE's own in `contract/wfe.swagger.json`, with the ontology agent's Read and Ask JSON Schemas, whose JSON Foundry carries as strings, in `contract/ontology_agent/` with their `VERSION`. `pnpm contract:sync` copies Foundry's contract and the schemas from `backend/`, and the WFE's from `WFE_REPO`, a checkout of hosted Helix's backend, which only Helix's maintainers have.

Next.js 16 differs from older versions. Read the matching guide in `node_modules/next/dist/docs/` before using an API you have not used here.

## Rules

- **The allowlist.** The browser reaches the WFE only through routes listed in `src/server/papi-allowlist.ts`: one entry per method and path, written exactly as in the swagger, with `{param}` matching one path segment. No wildcards, no prefixes. Add only routes the UI calls. Never add sign-in, SSO management, role changes or member removal. `tests/unit/papi-allowlist.test.ts` fails unless every entry is in the contract and served by the mock.
- **WFE types** live in `src/shared/wfe.ts` only, written from the swagger, under a heading per area. grpc-gateway JSON is camelCase, enums are names, int64 are strings, and default values may be missing.
- **Agent JSON** (Read results, Ask events and results) is the engine's, typed from `contract/ontology_agent/` in `src/shared/foundry-read.ts` and `wfe.ts` "Ontology: questions", and parsed without trust. The mock emits exactly those shapes, and `tests/unit/agent-contract.test.ts` validates every mock answer, every fixture and the reads the SPA sends against the schemas (`mock/agent-contract.ts`, ajv), so a contract change fails CI.
- **Calls** go through `api()` in `src/web/api.ts` with WFE paths (`api("/v1/whoami")`). It adds the CSRF header on unsafe methods and sends a signed-out user to sign-in.
- **Look.** Everything uses the kit, shell, tokens and copy tone (`src/web/kit`, `src/web/shell`, `src/web/workspace.css`). Build a new screen from the kit and an existing area's CSS rather than inventing styles, with colors as tokens. Do not edit the kit to suit one screen.
- **Colors** are `--hf-*` tokens in `src/web/workspace.css` only: the light set on `:root`, the dark set in two identical blocks (`@media (prefers-color-scheme: dark)` under `:root:not([data-theme="light"])`, and `:root[data-theme="dark"]`). A new color gets a value in all three, or is listed in `SAME_IN_BOTH`. No other CSS in `src/web` has a color literal (the landing page, `src/landing`, is dark only and keeps its own); `tests/unit/theme-css.test.ts` checks that, and the dark theme's contrast (4.5:1 text, 3:1 icons and marks).
- **Cookies** are Foundry's own and host-only: `__Host-foundry-session` (`WORKOS_COOKIE_NAME`), `__Host-foundry-csrf`, `__Host-foundry-login-<flow>`. On loopback http (mock, e2e) they drop the `__Host-` prefix. Never set a cookie domain.
- **Secrets** never go in the repo. `.env.example` names the variables. The values in `mock/env.ts` are mock-only fixtures.

## Adding an area

An area (Workspace, Data, Ontology) owns its folder (step 1) and adds to four shared files, each in a section of its own (steps 2 to 5):

1. `src/web/areas/<area>/`: `index.tsx` (route components; Data and Ontology export a `*Routes` table for their URL prefix, and Ontology also `ExploreRoutes` and `AskRoutes` for `/explore` and `/ask`), `paths.ts` (URL helpers, merged into `src/web/paths.ts`), `shell.ts` (sidebar children, a section's panel and command-palette sources), and its CSS.
2. `src/web/main.tsx`: the area's routes, if it adds a new prefix.
3. `src/server/papi-allowlist.ts`: one line per WFE route the area calls, in the area's section.
4. `src/shared/wfe.ts`: the payload types, under the area's heading.
5. `mock/routes/<area>.ts`: the same routes with in-memory state, spread into `mock/routes/index.ts`. Use `membership()` from `mock/state.ts` for workspace-scoped routes and `onReset()` for the area's state.

Then add the area's main flow to `tests/e2e/` and its logic to `tests/unit/`.

## Things to know

- Names and Records: wherever an entity shows (the Explorer's canvas, tooltips, inspector and search, Records, an entity's page, a document's view) it reads by the version of the load the page reads (`explore/naming.ts`, `useNaming(versionId)`): the first non-empty `names` prop of its type, else its key props joined, else its stored `name`, else a short id; a label the version doesn't know, or no current version, keeps the raw label and the explorer's own caption. `<prop>__nn` (normalized names), an entity's `entity_key` and `norm_name`, a fact's `fact_key`, anything's `foundry_load` and Foundry's other stamps (`foundry_*`, such as `foundry_tx`) on all but Foundry's own labels never show in property lists; those stamps (`isFoundryStamp`) also never match the Explorer's search or take its `contains` scan's keys. Records (`/explore/{id}/records`, `areas/records`) is the Explorer's table view: its types are listed in the Explorer's panel (above the table while the panel isn't on screen); every query in `records/model.ts`, each bounded (a page is `range` over one type, one row more than a page, at most 10,000 rows deep; searches and filters count up to 1,000).
- **Running Foundry locally**: `local/` (compose, README, `.env.example` of optional overrides) runs the local build, with nothing to set up: `docker compose up -d --wait` from the root (its `compose.yaml` includes `local/compose.yaml`: one project, `helix-foundry`, the same volumes from either place, and Compose reads `local/.env` for that file from either) or from `local/`. Its first service, `init-secrets` (`foundry init-secrets` in the foundry image, offline), writes the secrets the `secrets` volume lacks, once: an old install's `FOUNDRY_*` from its `local/.env` (setup.sh's, before 0.1.1), else random ones; every other service waits for it and reads its own from the volume (the site `FOUNDRY_LOCAL_TOKEN_FILE`, MySQL `MYSQL_PASSWORD_FILE`, the store its file, foundry `local.secrets_dir`). The connector key there seals every stored credential and is never made again. foundry makes the owner's first workspace, My workspace, until the install has had one, and with no `FOUNDRY_AI_PROVIDER` finds its AI default on the machine (`backend/ai/detect`: the shell's `ANTHROPIC_API_KEY`, then `OPENAI_API_KEY`, then an Ollama with a model that calls tools, then LM Studio; `none` is none). It runs the standalone `foundry` image (Foundry's backend in one process: its API, a directory of the one owner's workspaces, projects and databases, and its workers; built from `backend/`), the ontology agent, SeaweedFS, MySQL and the public helix-db image. That HelixDB keeps no tenants apart: every ontology's loads share one database. foundry also serves MCP and HTTP Ask on the REST listener the site calls, which `local/compose.mcp.yaml` publishes on the host's loopback (8081, or `FOUNDRY_MCP_PORT`) when asked, so a port taken there never stops the app, with the owner's site token as the bearer; MCP and HTTP Ask answer only for loopback, `host.docker.internal` and the host of `local.site_origin` (`integrationHosts`), while the site's routes are limited only by the token, its probes stay on the health listener, and the links agents get start from `local.site_origin` (compose's `HELIX_LOCAL__SITE_ORIGIN`, the site's `FOUNDRY_ORIGIN`). The site's `Dockerfile` builds its image.
- **Local build** (`NEXT_PUBLIC_FOUNDRY_MODE=local`, fixed at `next build`; `src/shared/deployment.ts`): a copy someone runs on their own machine. It has one owner and no sign-in, members, billing or sign-out. `/papi` (`src/server/local.ts`) answers only the Host of `FOUNDRY_ORIGIN`, which must be a loopback origin, and forwards as the owner with `FOUNDRY_LOCAL_TOKEN`, else the token in the file `FOUNDRY_LOCAL_TOKEN_FILE` names (read once it reads; shared with the API, 32+ bytes; the CSRF secret is derived from it) under the same allowlist, origin and CSRF checks. The API refusing the token is shown as a setup error, never a sign-in. Anything the hosted site shows about members, the plan or the Helix dashboard is behind `LOCAL`, as are People enrichment's settings (locally the API reads the setting as unavailable, so Edit offers no Enrich people). A local build offers no API source (`connectorKindsQuery` drops the `events` kind, and the palette has no New API source): local MCP supports the connector/document workflow; API source operations and their send tokens remain disabled.
- Refresh: Foundry access tokens live 300 s and WorkOS refresh tokens are single use. AuthKit refreshes 30 s before expiry, and a failed refresh while the token is still valid keeps the session. Once the token has run out, a second refresh of the same cookie fails and ends the session, so: every `/papi` answer says how long the token has left (`x-foundry-session-expires-in`, `src/shared/session-contract.ts`), and once that is under 10 s, or not known yet, `api.ts` sends its calls one at a time under a Web Lock shared by the origin's tabs until one reports a fresh token. That holds across server instances. On one instance, parallel calls also share one refresh per session cookie (`src/server/single-flight.ts`), and a rotated session is reused for 30 s by requests still carrying the old cookie.
- Onboarding: a workspace with no ontology shows nothing but the new-ontology wizard (`main.tsx`'s `WorkspaceRoutes`, `onboarding` on `useWorkspace()`). The sidebar keeps only the workspace switcher and the account menu (no nav, no search, no palette). Every other path redirects to `/ontology/new`, except an ontology's own pages (the one just created opens before the list has it) and `/settings/*` (the plan a database connection needs). It opens on Get started (`choosing` in `new-ontology.tsx`): the sample, then one section whose toggle (`Segmented`) starts on Set up with your agent (`AgentSetup`: Copy prompt), its other side Use my own data (Continue opens the wizard); a local build starts on Use my own data, and its agent setup goes through the install's own MCP (`local-onboarding-prompt.ts`). The Helix MCP's connector links (`/data?add=<kind>`) open their form over the wizard. To test the full app in the mock, sign in as `ada@example.com`; a new email lands in onboarding.
- Workspace switching is client-side (`src/web/workspaces.ts`): a Foundry session works on every workspace the user belongs to. When sessions become workspace-scoped, the token swap goes in `chooseWorkspace`.
- Links into the app may name their workspace with `?workspace=<id>`: `SignedIn` opens and remembers it when the user belongs to it, says so when not, and drops the parameter. `/data?add=<kind>` opens that kind's form in the Add data modal (`?add=1` the picker). The Helix MCP's `helix_foundry_connector_link` sends users to `/data?add=<kind>&workspace=<id>`, so connector credentials are entered here, never through an agent.
- Sign-out returns to `/login`. WorkOS must list `https://<host>/login/callback` as a redirect URI and `https://<host>/login` as a logout redirect for the Foundry application, and `https://<host>/connect/callback` as a redirect URI for connecting a source by signing in (below).
- Password, SSO and email-verification sign-in are not offered: the callback sends those cases to `/login?error=sso|verify`.
- Foundry Pro and Max (`src/web/areas/workspace/plan.ts`, which holds the prices: Pro $100 and Max $500 a month; the WFE returns none): one Autumn group, so a workspace holds Free, Pro or Max, and Max grants everything Pro grants. Autumn is the system of record and the WFE reads it live, so the plan query is cached for a minute. Every stamp's plans offer every connector kind (paid plans sync more often); the WFE refuses a kind a plan leaves out (create, test, update and sync) with FAILED_PRECONDITION and reason `FOUNDRY_PRO_REQUIRED`, which the mock keeps for PostgreSQL, MySQL and S3 on Free. The Data area renders `<ProGate feature="PostgreSQL connections" />` (`areas/workspace/pro-gate.tsx`) for a kind with `available: false` (the picker, and a Pro connection's page after the workspace left Pro) and in place of a form error for which `isProRequired(error)` is true. It links owners and admins to `/settings/billing`, and the billing page refreshes the connector kinds once the plan bought shows. A Max workspace passes every Pro gate, so it never sees one. The plan's tier shows on Plan & billing and the account menu.
- Billing: checkout (`CreateFoundryProCheckout`) sends a new `clientToken` per click and always the `tier` (`FOUNDRY_TIER_PRO` or `FOUNDRY_TIER_MAX`; unset is Pro). From Free, the upgrade dialog picks Pro or Max and takes a promotion code; a paid workspace switches to the other tier from its card, behind a confirm dialog, by checking that tier out (asking for the tier held attaches nothing). Cancel and resume act on whichever tier is held. After an answer that may have charged (`checkoutFailure` is `unsure`) the page reads the plan before offering checkout again, and Autumn refuses a second attach of a held plan. Stripe Checkout returns to `/settings/billing` (the WFE's `billing.autumn.foundry.return_url`), and that page keeps reading the plan for a while after a checkout this tab started, until the tier it bought shows. The mock's checkout and billing portal are `/mock/checkout` and `/mock/billing-portal`; `POST /__mock/config {"checkoutCardOnFile": true}` charges without a page.
- `/` on the hosted site, for a visitor without a session cookie, is the landing page (`src/landing`, from HelixDB/foundry-website), in a root layout of its own (`src/app/(landing)`) so the app's global CSS never reaches it, and going between it and the app is a full page load. Its ways in go to `/login`. With a session cookie, and in every local build, `/` redirects to `/ask` keeping the link's query (a session that has run out is the app's to send to sign-in). The SPA's own `/` is Ask too (`main.tsx` redirects it to `/ask`, keeping the link's query), on the ontology last opened, else the newest; a workspace without an ontology goes to the wizard. Ask is the sidebar's first section and is current on `/`, with its threads under the sections. There is no Home page.
- Mock users: `alan@example.com` is a plain member of Acme, for what non-managers see; `POST /__mock/config {"alanRole": "WORKSPACE_ROLE_ADMIN"}` makes him an admin until the next reset, for what admins (not owners) see. Any other new email starts with no workspace, named from the email unless the mock sign-in page's Name is filled in.
- Members are read-only here and invitations are create-only. Role changes, removal and pending-invitation management stay in the Helix dashboard (`NEXT_PUBLIC_HELIX_DASHBOARD_URL`, set per stamp in `next.config.ts`), where invitations also land.
- Access (hosted only; `areas/workspace/access*.ts*`, `mock/routes/access.ts`): Foundry's source grants (`backend/access`). Owners and admins grant a member, a team or an agent's key (the WFE's service credentials, made here with no project grants, the token shown once) sources: a connector (its tables now and later, and the sets it owns), one table, a document set, or People enrichment. A load holds its version's generation's tables and table files, the sets its documents are in now, and enrichment once it applied profiles (`uncoverable`: "Load again to share"); a grantee reads the part of an ontology's current load its own and its teams' grants hold (`holdsAny`, the backend's `Grants.Reaches`), all of it while they cover all of it, and changes nothing. Sources are the limit: giving a member or a team any restricts that member or its members (the store does it with the grants), confirmed first (`newlyRestricted`), and joining a team that holds some does too; taking them away leaves them restricted, since it must never give anyone more, and the Restricted switch lifts it only once they hold none, their own or a team's (the store checks that under the workspace's lock, which grants and team changes take too). An owner, an admin or a member with raw access is given none (`restrictable`), and a team with such a member none either, though owners and admins may sit on one, confined only if they stop being one. Grantees are members restricted in Settings › Access (plain members without project write or query access, `restrictable`) and, on Ask's and the graph's reads, members without query access. Settings › Access (`/settings/access`, owners and admins; its lists, dialogs and new keys are `data-replay-block`) has Agents, People (the Restricted switch; a restricted member who holds raw access again, given in the Helix dashboard since, is flagged Raw access, `holdsRawAccess`), Teams, each with Sources: the connectors and sets as a tree saved in one PUT, then what it can read (all, or "Part of it: not …") and what each other ontology reads (`readings`, `missing` in `access-model.ts`, the backend's `Grants.Missing`), and Ontologies, who each is shared with and who reads part of it. The shell reads `.../foundry/access/me` per workspace (`main.tsx`; its `ontologyIds` are `useWorkspace().granted`, its `partialOntologyIds` `useWorkspace().partial`), and again on coming back to the tab, once a minute old and when a job ends (`myAccessQuery`, `scope.tsx`): a grantee (`useWorkspace().grantee`) has only Analyst, Ontologies and the Explorer, no search, settings or onboarding ("Nothing shared with you yet"), `granteeRedirect` sends any other page to Ask, Records or the ontology's overview, which is its shared load's schema (`SharedOntologyHome`), and Ask has no Load picker. Through grants, a question's limits are the asker's own: `budget` on ListFoundryQuestions ($10 a month and 10 an hour, which the threads don't show and a question waiting on them says), and the WFE's refusals say nothing of what the workspace asked or spent. Getting into production's card shows only to someone who reads the database (`ChatBar`), and a grantee reads no generations, so `useSampleOntology` calls nothing the sample and it gets no sample banner. How a page reads an ontology's load is decided in one place (`useGraphReader`, `explore/graph-reader.ts`, from `readAccess` in `access-model.ts`): `database` (query-read; also whenever the member's query access, whoami's `projectAccess.queryRead` on `ShellWorkspace`, isn't known), `grants` (a grantee, or a member who can't query the ontology's project, on an ontology `granted` names) or `none` (`NotShared`; Ask's and the Explorer's ontology pickers and `/ask`, `/explore` offer only ontologies the user reads). `grants` reads the current load only (`LoadSelection.shared`: `?load=` ignored, no pickers) through `:read` typed reads, never query-read (`explore/typed-reads.ts`, run by `readQueries` and `recordQueries` for the same shapes; each request goes through `readGraph`, which sends an ontology's two at a time, as foundry-read refuses a workspace's past four, sends one refused 429 again after 0.5, 1, 2, 4 and 8 s, and throws `ReadFailed` for a paused database, or a 503 within a new database's window, as starting, so pages show those states as for query-read: `typedReadFailure`): an entity's props, facts per link side, the rows and quotes behind them and its rule breaks (no mentions or reviews: the page says so), names of cited entities, and Records (a count per type, reads of 200 rows by `offset` cut into pages, down to its 10,000 rows, text search of names); Records is the Explorer (the graph redirects there, no Graph switch), and a document opens as uploaded (`documents/shared-document.tsx`, its text from `:content`, no bytes or marks). Ask's citations open those pages; a rule break or a People enrichment profile opens its step (`CitationContext.shared`). Nothing a grantee opens calls a route the WFE refuses it or query-read (`access.spec.ts` checks the request log). Someone who reads only part of an ontology (`readsPart`, `useReadsPart`: grants that hold only some of its load) sees one quiet line saying so (`PartNote`) on its overview, Ask (a new thread and an existing one), Records, an entity's page and a document's. They name only what their sources fill: a restricted member's version comes projected (its definition only `format`, `status`, `ontology_toml` and a `mappings_toml` of its version lines, no generation or sets), anyone else's through the load's `view` read (`useNaming`, `graphReadQueries.view`, which also answers `partial`). A grantee who holds it all still reads the version without what drafting found and cost (`summary`, `usage`, `rules`, `parent_version_id`, each item's `rationale` and card). The agent narrows each read that touches something partly held (contract 4.6.0): a keyed entity shows only if a row they hold states it, or it has no rows and a document they hold names it; another only through what they hold; a property is the stored value when a row they hold sets it, whatever other rows do, else what the quotes they hold agree on, else nothing; a keyed type's `name` is the entity's id until they hold the type whole, so readable names come from its full `names` props; a relation stays only while every member link is held whole. Such a read can't be paged, since where a page ended would say how much they can't see: `offset` is refused, the engine reads further than asked and filters (1,000 rows, 100 where a step's link is partial), cuts to `limit` (100 where a column's values are settled), and its `total` is the rows shown, with `stats.matched` and `stats.patterns` 0, so nothing says whether more follow. Records tells such a type from the `view`'s `partial` (`typedNarrows`: the type, or a column it reads, a type held whole with one partly held column included): one read asking 200 rows, "The first 64 records you can read" or that none of those read are theirs, and no pages; a `?page=` is ignored. Everything else pages by `offset` with its total, as full access does (a window refused `/return/rows/offset`, the view being stale or unread, reads as narrowed). `countsPlan` gives a partly held type no count. ## Review decisions

- Reviews use their `review_key` for settle calls. Send only a `FoundryReviewChoice`; the backend derives the decision identity from the current load. The list returns flat camelCase decisions, 100 a page by last decision id, with no filter, so pages read it all; settling never waits for it. Only the current load can be settled; decisions and their removal apply from the next load ("Reload to apply"). A load reads the decisions saved when it was created (the backend snapshots them, and so does the mock, catch-up extracts included), so a decision saved before the shown load started was read by it: if its review is still there, what it chose isn't in that load, and the page says so instead of asking to reload.
- `reviews/model.ts` `settleable()` reads a review once, from its record and the entities it concerns (`FOUNDRY_CONCERNS`, read with the review): a `resolve` review (identity `type`, `doc_id`, `norm_name`), a `prop` review (`type`, `entity_key`, `prop`, `values`, and the entity's stored value), or `stale` when the identity the backend reads, or the entity, is missing (a load from before decisions: "Load again to settle this review"). Candidates are stored identities (a key's tagged encoding, such as `scus_…`), shown by the concerned entity's name and linked to its page.
- A property only a table row can hold through a conflict, so a `prop_conflict` whose entity has a stored value is a row conflict: its `values` list only the quotes that disagree with the table. The page says the table's value is kept and offers the documents' values as "Replace the table’s value with", warning that a decision holds in every later load, even after the table changes. It never offers to pin the table's value.
- An adjudicated resolution has an informational `FoundryReview` with reason `adjudicated`, its type, document, normalized name, chosen entity key and confidence; its only candidate is that entity. Treat it as a resolve review; "Undo link" saves `resolve: {notInData: true}`. Mentions marked `adjudicated` link to the document's review tab. Auto-adjudication stays off; the mock's opt-in `documentAdjudicated` fixture seeds a variant and its review for undo tests.
- Property-conflict `values` are the engine's JSON-encoded `PropQuote` records, including each value, document, span and quote. Parse them before offering a value; never send the whole quote as the value.
- The mock's settle route checks what the backend checks, with its codes (`mock/review-decisions.ts`): no current load and a review without identity, or whose type or prop the loaded version lacks, are `FAILED_PRECONDITION`; a chosen entity not in the load and a value the engine refuses are `INVALID_ARGUMENT`. A value is stored as the engine keeps it: strings trimmed (a blank one refused), dates `YYYY`, `YYYY-MM` or `YYYY-MM-DD`, datetimes in UTC (a UTC year outside 0000 to 9999 refused), `null` removes the value. Making a version current drops the decisions it doesn't take (an agent draft with types only), as the backend's set-current does; a newer draft alone changes nothing. Version 3's route lets documents state a customer's `currency`, which the customers table sets: "<customer> is billed in GBP." in a document makes a row conflict.

## Backend

`backend/` is the Go module `github.com/helixdb/helix-foundry/backend` ([backend/README.md](backend/README.md)): Foundry's API, its workers, its MySQL store and migrations. Its checks run in `backend/`: `go build ./...`, `go vet ./...`, `gofmt -l .` (prints nothing), `golangci-lint run ./...` (v1.62.2), and `go test ./...` with the test databases up (`docker compose -f compose.test.yaml up -d --wait`). After a `.proto` change, `buf generate && buf generate --template buf.internal.gen.yaml` regenerates `pb/gen`, which is committed. `.github/workflows/backend-check.yml` runs the checks and the regeneration on every change; `.github/workflows/backend.yml` runs the tests and builds the image (`docker build backend`) on changes to `backend/`.

- Hosted Helix imports this module and runs it inside its own server. REST paths, verbs and JSON shapes, SQL and transactions, migration versions, config keys, environment variable names, metric names and worker schedules are shared with that deployment: change them on purpose, never as a side effect.
- The module imports only its own packages, the standard library and public modules. What differs when hosted (sign-in and roles, workspaces, Helix databases, plans) comes in through the module's interfaces.
- `integration/` is the Foundry MCP's tools and HTTP Ask (`contract/foundry-integration.openapi.json`, `examples/ask_tool.py`), shared with hosted Helix; `local/integration.go` serves them on an install. `Service.Events` says the host has API sources: without it no tool, description or schema names them (`foundry_schema.go`), and a tool reads none of their methods, which an install doesn't serve. Every other method a tool calls must be in `local/methods.go` (`local/integration_test.go` checks).
- Migrations are embedded from `store/migrations` (goose). Hosted runs them in one sequence with its own, so a new migration takes a version later than every existing one, and a shipped migration is never edited or renumbered.
- Source grants (`backend/access`): `Register` runs every method through the access check, so a grantee (`SOURCE_GRANTEE`, a restricted member, or a user or key a host sends as one) reaches only what `access.RuleOf` admits, deny by default; `access.GranteeAdmits` tells a host which methods a refused caller may be sent to as a grantee. Giving a member or a team grants restricts them in the same transaction, and taking grants away never lifts it. A host implements `People.Member` (role, and whether the member reads databases outside Foundry), stamps a key's `service_credential_id`, and calls `DeleteFoundryAccessPrincipal` when it revokes a key and `RemoveFoundryAccessMember` when it removes a member. A new method needs a rule in `access/rules.go` (its tests fail until it has one).
