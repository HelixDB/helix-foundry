# Vendored ontology agent contract

These files are copied unchanged from the ontology agent's source, `proto/ontology_agent/v1/`, at commit `a51ecfcfb18f91a2ba889daff3e131b77df026e9` (contract 4.16.0: 4.2.0 and fourteen minor steps. 4.3.0 and 4.4.0 add `Audit`, which audits a page of a load's documents for what their reviews say the bundle lacks, `Check`, which checks a self-healing draft against its proposal, and Revise's `origin`, the approval of a self-healing fix; the foundry-heal-worker calls `Audit`, and Foundry calls no `Check` and sends no Revise `origin`. 4.5.0 lets an Ask request set what each read of the graph may spend, `limits.read` (`wall_ms`, `scan_entities`), and a read stopped at one, or at `helix.timeout_secs`, names it in its `tool_result`'s error. 4.6.0 adds `Read` and `Ask` taking `visibility`, what a reader holds of a load, the `view` read and the `not_visible` failure, and a query's rows taking `offset`, which a reader of part of a load can't use; a reader's Ask reads within the same `limits.read`. 4.7.0 adds valid time to `Ask`'s result: a cited version's `valid`, when its state held in the world (`from`, `to`, and `day`, a source's day with no time of day, whose `from` is the next midnight UTC), and every `cannot_answer`'s `kind`, what the load lacks (`uncovered`, `after_as_of`, `undeclared_relation`, `undeclared_property`, `absent`). Any Ask with `visibility` (every grantee's question, whoever holds all of the load included) is offered no `history_of`, `changes` or `helix_query` and no `get_entity` `as_of`, and answers another time from what `get_entity` shows; a reader of only part of a load also sees no `valid` or `past`, so its questions about another time or a change end `cannot_answer` with `kind` `uncovered`, and one about a time after it asked still `after_as_of`. `valid` is new on a type that refuses unknown fields, so a check against 4.6.0's schemas refuses an answer citing one. 4.8.0 gathers a relationship no link covers under the longest name of the ontology's links its suggestion starts with, so one finding holds every form its reports took: an `unmatched` signal always carries `spellings` (canonical, at least one), a route proposal `gathered` and a draft proposal `origin` (`finding` or `asked`). A finding's fingerprint holds the name it is gathered under, so it moves with the ontology's links: the foundry-heal-worker unions a finding's spellings over the load's pages, a complete audit replaces the findings it no longer finds (superseded) rather than summing old and new, and a dismissal holds only for the spellings it was dismissed with. `Check`'s result gains `card`, which comes with a description draft that passed, and `arms.more_fresh`; a description draft's `gate: pass` now means only that it does no clear harm and a person decides. All of these are required, so a check against 4.7.0's schemas refuses them. 4.9.0 holds back a claim a document's commit can't trust as a review, writing nothing of it: `Compare` lists one more kind, `held`, each held claim by its claim key, and a held review a load stored before 4.9.0 is keyed by its review key, so such a load's held claims differ from a 4.9.0 rebuild's until it is rebuilt too; the graph worker counts a rebuild that differs only there as `held`, not `drifted`. Ask shows held claims to its model in `history_of` and `changes` as untrusted text no answer can cite, so `AskResult` is unchanged. The schemas change only in descriptions. Visibility was first vendored from `0cd3dff66a2275c2841ace8d861fdfc967c40cb7`, which called it 4.3.0, a number dev-3's heal contract already had: an agent built from that commit reports 4.3.0 and isn't this contract. 4.2.0 was 4.1.1 and graph apply, all additive: `Ingest` takes `reload: "diff"`, which brings a load up to new data in place, and a `changes` source access, a table's changes since a position; it answers `applied`, `diff_unsupported` and `position_mismatch`. `Extract` takes `remove`, documents to retract from the load. `Compare` compares two loads of one version). Its `schema/catalog.json` prices OpenAI's and Amazon Bedrock's models as well as Anthropic's; Azure deployments are priced from OpenAI's rows, and a Bedrock inference profile with no row of its own as the model it runs. The `ontology-agent` image Foundry runs beside its workers must be built from a commit that serves this contract. 4.10.0 links a document's party written with a legal form its row lacks to that row, with a review a person can overturn: `legal_form` joins `DocumentCounts.resolved`, as a mention's `resolved_by` and as a review's reason, which settles as `adjudicated` does. 4.11.0 adds a person's release: `Extract` takes a `release` decision naming one review of a document by its `claim_key` and its quote's `section`, `start` and `end`, a held fact's review carries `statement` (its ends in order and its properties), and a document's event counts `released`, `release_refused` and `release_missed`. 4.12.0 says what became of each release: a document's event lists `releases`, one entry for each release decision sent with the document, by its `decision_id`: `written`; `refused`, with the `reason` its reviews stay held; `missed`, when the run committed the document and its commit held no review at the decision's place; or `not_held`, when the load held the document already and holds no such review, as a release sent again finds. A resend job (`foundry_load_jobs.kind` `resend`) applies a person's approval to the load that holds its document by sending the document again with its artifacts and nothing to spend, and records each entry on the load's decision (`foundry_load_decisions.applied_status`). 4.13.0 links a document's name that is part of one row's name (`part_name`), and an entity the text calls only by an identifier the verifier held back (`own_name`), to that row, each with a review a person can overturn: both join `DocumentCounts.resolved` (required; an own-name link is no longer in `identifier`), a mention's `resolved_by`, a review's reason, which settles as `legal_form` does, and a release's refusal `reason`, as an approval at such an end is refused, whatever its link holds, until a resolve decision settles the name. A name one row holds less firmly is `ambiguous`, offering that row alone. Foundry reads both counts and stores neither. Rolling back to a 4.12.0 Foundry and agent after loads were built on 4.13.0 leaves them current: a 4.12.0 engine counts a `part_name` or `own_name` mention as the document naming the row, so a reader who holds only that document is shown the row until the load is built again, which Foundry can't hide; rebuild every load built on 4.13.0, or make a load built on 4.12.0 current. Until then their `part_name` and `own_name` reviews can't be settled: the old site shows them as "Held for a person to check" with no controls, and an approval refused for either reason as the raw word ("The load kept it held (part_name)."). 4.14.0 changes what a release does on a link that holds one value, and its schemas only in descriptions: the approval is a decision of the link that takes effect from the date its quote gives, else its document's date, else `decided_at`'s day, so an approval never moves a claim forward in time. It beats undated statements and those dated up to that date and displaces the edge it conflicted with (whose evidence stays), so a claim held as `conflict` on such a link can be released, and Foundry offers to approve it. A statement dated later beats it: the approval's quote is then kept as evidence alone, and its outcome is still `written`. A quote dated after the load records it is not yet in effect and beats nothing, so its approval can't displace another value the link holds. Of two approvals of one link only the later `decided_at`, then the `decision_id` that sorts last, is the link's decision, so Foundry sends a decision's own `decided_at` in every Extract; the other's quote still states the link from its own date and beats that decision if it is dated later. The schemas' `decided_at` description predates the dating by the quote and speaks of `decided_at` alone. A release whose `claim_key` names no review of its document is matched by its place and `statement_hash`. A property's `prop_conflict` review is now written whenever its rows and quotes disagree, decision or not, so a load given a value decision holds and counts it, and the site shows it as settled by that decision. Stored, additive: the quote a release writes for a one-valued link keeps `decision_id` and `decided_at`; an engine before 4.14.0 reads it as a plain quote. Rolling back past 4.14.0 needs a rebuild first: an older engine can't weigh decisions, so removing or replacing an approved document there empties its link (the approved edge goes and the one it displaced is never restored), and a later commit there can move the edge. Before such a rollback, rebuild every load holding an approval on the older engine, or make an older-built load current. Rolling forward to 4.14.0 again doesn't repair a load the older engine committed to: only a rebuild, or a new statement of the link, settles it. Rolling out 4.14.0 also changes what approvals saved under 4.11.0 to 4.13.0 do, with no one acting: every new load, and every resend of an approval's document (any approval of another claim in it makes one), sends each with its stored `decided_at`, and on a link that holds one value the newest becomes the link's decision. It displaces statements of no date, a first snapshot's table rows, and statements dated up to its own date, so an approval refused as `conflict` before is written and takes the link, in place on the next resend of its document; one kept as evidence alone stays so where a statement dated later holds the link. A load updated in place reads approvals an earlier engine wrote as plain quotes until it is rebuilt. Foundry rewrites no saved row: a person removes an approval they don't want to decide its link. 4.15.0 adds `Assess`, a unary call that judges how much the ontology helped one of Foundry's workflow runs (its request, the calls it made with the run's id and its answer) on the workspace's question model: the foundry-ask-worker calls it for each finished run, and an agent before 4.15.0 answers it Unimplemented. No other request, event or result changes. 4.16.0 lets a person take back an approval a release wrote: `Extract` takes a `withdraw` decision, the release decision exactly as it was sent with `kind` `withdraw`, which takes back what that release wrote, before the request's documents are read and with no model call, so the load holds what one that never had the approval holds (a claim held for a `conflict` with a document since removed stays written as its document's own statement, without the approval's rank). A document's `releases` lists each withdrawal first: `withdrawn`, `not_written` (the load holds nothing the approval wrote: never written, taken back already, or another decision wrote the claim since), or `refused` with `differs` (quotes a release before 4.16.0 wrote of several claims of its link keep nothing to tell them apart) or `too_large`; the counts count releases alone. A request naming one `decision_id` as both a release and a withdrawal is refused. Approving again is a new release decision with a new `decision_id`. A removal now also takes the rank from an approval held for a `conflict` with the removed document alone. Foundry sends a withdraw when a person takes back an approval the current load may have written (the load's copy of the release becomes kind `withdraw` in `foundry_load_decisions`, sent by a resend job, its outcome in `applied_status`), and when a load becomes current holding such a copy of an approval taken back since. Stored by the engine: origin `hold` transactions, a review restored under one, and a quote's `decision_id` and `decided_at` removed where an approval stops ranking. Rolling back past 4.16.0 (a 4.15.0 Foundry and agent move together): an older engine can't read a withdraw, and an older Foundry can't read a `withdraw` row, so every Extract of a load whose list holds one fails. Before such a rollback run `DELETE FROM foundry_load_decisions WHERE kind='withdraw';`, then rebuild every load an approval was taken back from, or make a load built before it current: a take-back that had not run leaves its approval written there, with no decision left to take it back.

| File | What it is |
|---|---|
| `agent.proto` | `ontology_agent.v1.Agent`: `Turn` streams events then one result; `Ingest` creates a load and fills it, `Extract` adds documents to a load and `DeleteLoad` removes one, the same way; `Read` reads a load with its version's rules applied, and `Compare` two loads of one version, both unary; `Ask` answers one question over a load, streaming events then one result; `Clues` streams the people a load's `[enrichments]` item could look up; `Revise` dry-runs edits of a draft against a load, unary; `Audit` audits a page of a load's documents (the foundry-heal-worker calls it) and `Check` a self-healing draft, both unary; `Title` writes a generation's title, `Probe` checks an endpoint's models for each role and `Assess` judges a workflow run, all unary; `GetInfo` reports the contract version and the provider kinds the build calls. `Turn`, `Ask`, `Extract`, `Title`, `Probe` and `Assess` run on the models their request names, the endpoint's key in the call's `x-foundry-model-key` metadata |

Do not edit them here. To move to a new agent build:

1. Copy `agent.proto` and every file in `schema/` from the agent's commit and update the commit above.
2. Set `ontologyagent.ContractVersion` (`ontologyagent/contract.go`) to the first field of `schema/VERSION`.
3. From the module's root, run `buf generate && buf generate --template buf.internal.gen.yaml`, then `go test ./ontologyagent/`. The tests check every request the workers and foundry-read build against the request schemas, the fixtures the decoders are tested on against the result and event schemas, and the version against `VERSION`.
4. Build the agent image from that commit and deploy it with this backend.

Each generation, graph job, read, question, title, probe and assessment checks the sidecar's `GetInfo.contract_version` first, and that `GetInfo.providers` holds the workspace's provider kind. While it differs from `ContractVersion`, every generation, graph job and question the workers claim fails for good and every read is refused, so deploy the image and the backend together.
