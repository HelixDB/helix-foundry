# Helix Foundry backend

The Go module `github.com/helixdb/helix-foundry/backend`: Foundry's API and the workers behind it. They connect and sync data sources, have the ontology agent draft and revise ontologies, load versions into HelixDB, read documents, answer questions over a load and email people when their work is done. State is in MySQL (`store`, with its migrations embedded from `store/migrations`); synced tables and documents are in S3-compatible storage.

## Build and test

Go as in `go.mod`, and Docker for the test databases.

```sh
go build ./...
go vet ./...
docker compose -f compose.test.yaml up -d --wait   # MySQL on 3307 and 3309, PostgreSQL on 5433
HELIX_TEST_ROOT_DSN='root:helix@tcp(127.0.0.1:3307)/' go test ./...
docker compose -f compose.test.yaml down -v
```

`docker build .` builds the standalone image.

The generated code in `pb/gen` is committed. After changing a `.proto` under `pb/proto`, regenerate it with [buf](https://buf.build):

```sh
buf generate && buf generate --template buf.internal.gen.yaml
```

## Run it

[`../local`](../local) runs Foundry on one machine: the site, this backend, the ontology agent, MySQL, SeaweedFS and HelixDB. It runs Foundry's release images; with `FOUNDRY_SITE_IMAGE=helix-foundry/site:local` and `FOUNDRY_IMAGE=helix-foundry/foundry:local` in its `.env`, `docker compose build` there builds the site and the backend from this checkout instead. The image's `foundry init-secrets --dir DIR` writes an install's secrets once (the compose file's first service), and `local.secrets_dir` (`HELIX_LOCAL__SECRETS_DIR`) reads them; with no `foundry.ai.default.provider`, `foundry` finds its AI default on the machine (package `ai/detect`).

## Questions a generation waits on

The ontology agent may end a draft's turn asking what only the user can answer (`needs_input`). The generation then stores no version and waits, still its ontology's live generation, with the agent's session state (`foundry_ontology_generations.turn_state`, never sent over the API: it may quote the data) and the questions. Every agent's question has one shape (`agentquestion`): an answer in words, or a choice of 2 to 20 options (labels, each with an optional description) of which the person picks one, or several when the agent made it `multiple`, the agent's `recommended` answer marked (a label, or for an answer in words its suggested words; the engine names it `default`), and always their own words instead (one) or as well (several); `agentquestion.Check` checks answers (`{question_id, options, text}`) against the questions asked. `AnswerOntologyGeneration` (`POST .../generations/{id}:answer`, naming the `question_round` it answers, or the MCP's `answer_generation_questions`) queues it with the answers, and the next attempt sends the state back with feedback on the draft revision asked of; `CancelOntologyGeneration` (`:cancel`) ends it instead. The Assistant asks people only through its `helix_foundry_ask_person` tool (`agent/ask.go`: 1 to 4 questions of its own, or a generation's waiting round relayed as its agent wrote it), which ends its turn (`asked`, finished reason `asked`); the person's answers are the thread's next turn (`SendFoundryAgentMessage` with `answers`, kind `answers`), and a relayed generation's become its `answer_generation_questions` card unchanged, the only way the Assistant answers a generation. Questions no one answers in `foundry.ontology.answer_days` (7) take their recommended answers (or are left to the agent): the `foundry-ontology-worker` answers them on its next tick and carries on. Each answer pays for another turn, so a turn that asks once a generation has had `foundry.ontology.max_question_rounds` (3) rounds fails it. A first draft that loads once ready (`load_when_ready`) emails its requester at its first round (`ontology_questions`, from the `foundry-notify-worker`), since they have left the page. A start of a new version names the sources the current version wasn't drafted from, so the agent asks about those first.

## Hosted Helix

Hosted Helix (foundry.helix-db.com) runs this same code as a library inside its own server. It runs the module's migrations in one sequence with its own, and supplies what differs when hosted, such as sign-in and roles, workspaces, Helix databases, plans and the provider accounts connectors sign in with, through the module's interfaces. So REST paths and JSON shapes, tables and migrations, config keys, environment variable names and metric names are shared with the hosted deployment: change them on purpose, never as a side effect.

Where the host supplies `ports.ProviderAccounts` (hosted: WorkOS Pipes), GitHub and Linear connectors can be connected by signing in at the provider instead of entering a key: the account stays with the host's broker, and the connector asks it for a token each time it reads. The sync worker checks each account weekly and deletes, through the broker, the accounts deleted connectors and failed sign-ins let go. A standalone install has no broker, and every connector takes a key.

Foundry's emails go out through the host's mail (`ports.Mail`) from the `foundry-notify-worker` (package `workers/foundry-notify-worker`), which hosted runs as a task beside the sync worker, with `foundry.notify.site_url` set to the site's origin. It tells the person who asked for an ontology's first draft to be loaded when ready how that ended, and follows up once, a day later, with someone who watched the sample and brought no data of their own. A standalone install sends no email and doesn't run it.

The same worker sends the reminders a person asks for on the landing page, from a phone, to try Foundry on a computer (package `reminder`, table `foundry_reminders`). The site sends each request to the `foundry-events` door, `POST /v1/reminders` (`{"email", "time_zone", "consent": "remind-v1", "client"}`, answered `{"next_send_at", "again"}`) and `POST /v1/reminders/stop` (`{"email"}`, at each sign-in), with its secret as the bearer. The door holds no secret: it passes the bearer's SHA-256 to `FoundryEventsService.CreateFoundryReminder` and `StopFoundryReminders`, which compare it with `foundry.reminders.secret_sha256` (empty: no new reminders, and the door answers 404). Each address gets one schedule: the first reminder at the next weekday 09:00 in the person's zone, then one each `foundry.reminders.gap_days` (7, 14 and 28 days) after the one before, stopping when the person signs in or unsubscribes, and never sooner than `min_gap_days` after the last when it asks again; at most about `max_new_per_hour` schedules start in an hour, and `max_new_per_client_per_hour` for one `client` (the site's key for a visitor's address). The secret is 64 lowercase hex digits (`openssl rand -hex 32`), and the door refuses any other bearer before it takes room. They go on their own subscription topic, `ports.TopicFoundryReminder` (`foundry-reminder`), which the host's SES contact list must hold before a deploy sends one, and whose unsubscribe footer is the host's. The door's ingress must route `/v1/reminders` as it routes `/v1/sources/`.

Self-healing audits run in the `foundry-heal-worker` (package `workers/foundry-heal-worker`), which hosted runs as a task beside the graph worker, on its ontology agent sidecar. With `foundry.heal.enabled` it audits each ontology's current load with the agent's Audit as the load becomes current and nightly, never while a graph job is live on the ontology, and stores the findings (`foundry_heal_findings`, `foundry_heal_runs`) the Suggestions page lists. A relationship's finding gathers every spelling its reports took (contract 4.8.0), and its fingerprint holds the declared name they're gathered under, so it moves with the ontology's links: each complete audit replaces the findings before it rather than summing with them, and a dismissal holds only for the spellings it was dismissed with. The first complete audit of a load on 4.8.0, as the load becomes current or nightly after the deploy, re-keys its findings so; until then the Suggestions page shows the earlier audit's. Off, the default, it does nothing, so a host may list the task everywhere. A standalone install runs it only with the flag on. Known limits: Foundry stores no source fields, so no audit checks source drift; and a run makes one Audit call per 1,000 reviewed documents, about 17 minutes for 1M at 1 s a page and hours at a 1 request a second plan rate limit, stopping incomplete after 4 hours; and a run stops once a graph job starts on its ontology, so an ontology whose jobs come more often than an audit takes (a connector syncing changes every few minutes) may never complete. Audits that resume across runs would lift both.

## Founder

Founder is Foundry's own agent, which a person talks to in the site (package `agent`, where the Go names still call it the Assistant, tables `foundry_agent_*`). The `foundry-agent-worker` (package `workers/foundry-agent-worker`, role `Roles.AgentWorker`) claims the turns of `api` threads (a turn has its thread's runtime, so a later helper claims its own) as questions are claimed, under `foundry.agent`'s caps (a turn's `max_usd`, `max_steps` and `max_wall_secs`, a user's `per_hour`, a workspace's `monthly_usd` and `max_running`; a reply runs at most 8 tool calls and a turn asks at most 3 Analyst questions), and runs each on the workspace's provider and its ask model (package `agent/llm`), never through the ontology engine but on the wire the engine uses for the kind: Claude on the Messages API (anthropic-sdk-go), OpenAI and Azure OpenAI on the Responses API (openai-go; Azure on its resource's v1 API with the `api-key` header), an OpenAI-compatible server on Chat Completions or Responses as its owner chose, at most its `max_calls_in_flight` at once from a process (per setting, so workspaces naming the same server never share slots), Ollama on its native `/api/chat` with `num_ctx` set to the setting's window (Ollama's `/v1` can't set one and would cut the prompt silently), one call at a time, and Bedrock on Converse with its API key as a bearer token (no SigV4, any model Bedrock serves; cache points for Claude's). Every call dials through the deployment's guard (hosted, public addresses only, at call time) and no client reads `ANTHROPIC_*`, `OPENAI_*` or `AWS_*` from the environment. A model with a window (Ollama's) bounds the transcript a call sends to three quarters of what the window leaves; earlier turns go first, and a turn whose own work passes that bound (or `context_tokens`) ends with `context` before the call the window would cut. A model's reasoning goes back only to the same model at the same endpoint, and on a Responses API only while the setting reasons. While the model writes, its text shows as `text_delta` events every 250 ms, which the step's `text` events replace (`FinishFoundryAgentText` drops them); the transcript is what was said. A delta that can't be written waits for the next: only a lost lease ends the call. While `foundry.agent.enabled`, the foundry-ask-worker's probe of a saved setting the agent passed also checks its ask model calls a tool on this wire (`llm.CheckTools`: up to 3 answers before it records one that doesn't, within `config.AIToolCheckTimeout`, which `foundry.ai.probe.lease` must cover past `AIProbeOverhead` while the Assistant is on) and records it in `probe_report.assistant` (`ai.AssistantCheck`, the API's `assistant_check`): a failed check never fails the setting, and refuses Founder's turns on it, saying why. Its tools are the MCP's, a closed list of them (`agent.Tools`), served in memory as the person who sent the message, in the turn's workspace alone: the host opens them through `integration.SessionHost`. It changes nothing itself: `prepare_operation` under `integration.ConfirmByPerson` hands the confirmation to a sink that seals its token with the connectors' keyring and shows the person a card, and the site's `:execute` runs it once, as the clicker, through the same port with `ConfirmByCaller`, then queues the turn that goes on from its result. The one exception is `agent.autoRun`, a closed list: a `create_dashboard` in the turn's workspace, in a turn of a message the person wrote holding the word dashboard or dashboards, runs at once as the person, as an approved workflow action runs (re-authorized, its confirmation consumed once, a replay finding how it ran); a new dashboard is always unpinned and unpublished, its `action_card` and `action_result` events say `auto`, the model is told to give its link, and the site offers Undo (it deletes the dashboard with the API's own `DeleteFoundryDashboard`). Updates, pins, publishes, deletes and every other operation stay cards. It prepares the operations `agent.Operations` names (every one the MCP has but `upload_document` and `create_event_source`), and its model's schema for `prepare_operation` lists those alone; in a workflow's turn it runs at once what its owner approved for the step. Each card's `display` is Foundry's names for what the action acts on (`agent.Cards`, `agent/display.go`, one shape per operation), drawn when it is prepared and again, as the clicker, when `:refresh` renews its confirmation; its ontology must be one the workspace holds; `target_named_by_user` says whether the person named its target (its id, or its whole name) in the thread; a `settle_review` is checked against the review as the current load holds it (`ListFoundryReviews`, with the entities it concerns), read as the person; and a `generate_ontology` reading every connector is refused while the workspace holds the sample company's (`integration.SampleDatabase`), which is read only when named. A replayed prepare finds the card its turn stored and draws nothing again. A tool call that never ran is shown as a `tool_result` whose `not_run` says why (`agent.NotRunReason`). An ask or `get_question` that returned names its Analyst question on its `tool_result` (`question`: `ontology_id`, `id`, `load_id`, `thread_id`, `status`), whatever the output's size, so the site shows the Analyst's own answer in the conversation.

On a standalone install, a workspace's owner may run its new threads on the Claude Code or Codex subscription they are signed in to, on their own computer, instead of the workspace's model (`agent.Hosts`, `local/agent_host.go`, the helper in [`../agent-host`](../agent-host)). A thread keeps its runtime (`api`, `claude_code`, `codex`); the worker claims only `api` turns. Codex runs with the owner's own Codex setup, so choosing it needs their confirmation once (`confirm_codex`, kept as `codex_confirmed_at`, else `FOUNDRY_AGENT_CODEX_UNCONFIRMED`; a card can't give it), and a helper runs it only at `agent.MinCodexVersion` or later: its account says Codex's version, and an older one is shown `outdated` and left out of what the helper runs (`agent.Runnable`), so no claim leases it a turn; one of no version (it didn't start) isn't outdated, but is left out too. The owner pairs a helper with a one-time `hxp_` code (`CreateFoundryAgentHostPairing`, ten minutes), which it spends for an `hxh_` token; the directory keeps each code's and token's SHA-256 alone (`local/directory/migrations/00003_agent_hosts.sql`). On the integration listener, the helper long-polls `POST /agent-host/claim`; a claim leases a due turn of its runtime to a lease owner of its own under the Assistant's caps, opens it (its message in the transcript once, the system prompt, the CLI session to resume, and the thread in words for a CLI that lost it), and mints an `hxr_` token bound to that claim: `/mcp` takes it for the Assistant's tools alone, as the turn's person, in its workspace, prepare-only, 25 calls and 3 questions, until the lease ends or the turn does; Foundry records each call as the worker does, and the helper reports only its model's text and how the turn ended (`renew`, `text`, `finish`). A claim of a turn whose earlier claim showed anything ends it as interrupted rather than run it twice; past its wall time, Foundry ends it. Revoking a helper stops its token and its turns' at once. A helper's turns cost nothing (their `max_usd` is 0) and count toward `per_hour`, steps and wall time. Sending in a helper's thread is `FOUNDRY_AGENT_HOST_OFFLINE` while no helper running it has called in 30 seconds. Hosts without helpers (`api.Deps.AgentHosts` nil) refuse the runtime routes (`FOUNDRY_AGENT_HOSTS_LOCAL_ONLY`) and run every thread on the worker; `integration.Service.AgentHosts` registers `helix_foundry_get_assistant_runtime` and the `set_assistant_runtime`, `pair_assistant_helper` and `revoke_assistant_helper` operations only where it is set.

`foundry.agent.enabled` is off by default: sends are refused (`FOUNDRY_AGENT_DISABLED`) and the worker claims nothing, so a host may list it everywhere. A standalone install turns it on, with its sessions in-process (`local.AgentSessions`). A host that turns it on implements `integration.SessionHost` for the worker's process and the API's (see its doc comment) and passes it as `api.Deps.AgentSessions` and to the worker through dig, with `ports.Databases` for actions on an existing database.

## Dashboards

A dashboard (package `dashboard`, tables `foundry_dashboards` and `foundry_dashboard_shares`, `api/dashboards.go`) is a spec of up to 20 tiles in rows of 1 to 3, each one typed query (the read contract's `Query`, the `query` read of `ReadFoundryGraph`, as an Analyst answer records its visuals' queries) of an ontology's current or a pinned load, shown as a table, bars, a line or a figure. It holds queries, never data: the site reads each tile through the load's `:read` as the person viewing it, so a dashboard shows no one more than they may read. Every member sees every dashboard (a grantee of source grants only the pinned ones); a member creates dashboards and changes their own while unpinned; owners and admins change any, pin up to 20 in every member's sidebar, and publish one. A workspace keeps 200. Edits, pins and publishes name the revision they were made from, so what is pinned or published is what its owner saw. An edit checks only the tiles it adds or points at another ontology or load (`Spec.NewTargets`): a tile whose pinned load or ontology went since blocks no other edit. A member deletes their own dashboard only while it is neither pinned nor published.

Publishing (`:publish`, owners and admins, with `foundry.dashboards.public_enabled`, on by default; a standalone install never publishes, `config.PublicDashboards`) reads every tile as the publisher, who must be able to query each tile's database, and keeps the outputs as a snapshot that names no workspace, ontology, load, entity or person by id, and keeps each query's shape only, never a value it tested such as `start.ids` (`dashboard.NewSnapshot`, `PublicQuery`; at most 512 KiB a tile and 2 MiB in all). Its transaction locks the ontologies its tiles read, as deleting one and turning People enrichment off do, and refuses (`FOUNDRY_DASHBOARD_TILE_FAILED`) when one was deleted meanwhile or has a purge pending. Its link's token is `hxd_` and 256 random bits: the table keeps its SHA-256, which a request is looked up by, and the token sealed with the connectors' keyring, so owners and admins are shown the link again. Republishing refreshes the snapshot at the same link; unpublishing (allowed with the flag off, so a link ended then stays ended), deleting the dashboard, deleting an ontology it reads, turning People enrichment off when one it reads ever applied profiles, or the workspace's deletion deletes it, and turning the flag off stops every link at once. The `foundry-events` door serves it, with no session, at `GET /v1/shared-dashboards/{token}` (`services/foundry-events/shared.go`: the address's bucket, 10 links that show nothing a minute, CORS for any page, never cached): its ingress must route `/v1/shared-dashboards/` as it routes `/v1/sources/`. A host's MCP sets `integration.Service.PublicDashboards` from `config.PublicDashboards`, and its registry gives every dashboard method `PermissionWorkspaceRead` and a principal (the handlers decide by role, through `ports.People`), with the caller's query-read scope resolved for the preview and the publish, as for `ReadFoundryGraph`.

The MCP lists, gets and previews dashboards (`helix_foundry_list_dashboards`, `helix_foundry_get_dashboard`, `helix_foundry_preview_dashboard_tile`) and prepares `create_dashboard`, `update_dashboard`, `delete_dashboard`, `pin_dashboard`, `unpublish_dashboard`, and where offered `publish_dashboard`; a user who manages nothing of the workspace gets the prepare tool with the first three only (`integration.memberOperations`). Founder offers the same, each a card its person runs, but for a new dashboard the person's message asked for, which it makes at once (`agent.autoRun`). No tool returns a public link: a tool's output reaches an agent, its model provider and its transcripts, so the link is shown only on the dashboard's page in Foundry.

## Workflows

People and agents read "workflow" for what the code calls an automation, and "use case" for what it calls a workflow (an outside agent's tracked task, shown on the ontology's Usage page): Go names, RPCs, tables, reason codes and metrics keep the code's words.

It runs only once its owner approved its spec with a click in Foundry (`:approve` takes a person signed in to the site, never `SOURCE_MCP`; no MCP tool approves): a spec edited by anyone or anything else waits for that click. The Assistant's card is that click too: the API approves exactly the steps a `create_workflow` or `update_workflow` card showed once its person runs it, and nothing for an edit whose card showed none (a new name or description). No step may start the work its trigger waits on (a sync of its connector, a load of its ontology), or each run would start another; loops through other automations, or through the refresh load a run's sync owes, are skipped as they fire (below). An Assistant step runs unasked only what fits an action the owner approved for it (`allow`, `automation.Fits`: the same operation and target, its payload bounded by its kind); a publish, approved or an action step, refreshes only the revision already at the dashboard's link, so an edit no one published since is never published unattended. Anything else it prepares waits for the owner as a card in the run's thread.

The `foundry-automation-worker` (package `workers/foundry-automation-worker`, role `Roles.AutomationWorker`, with `foundry.automations.enabled`; a standalone install runs it) fires schedules due (one run however long it was due), finds each event trigger's ended work by a cursor over its target's own index, counted once `settle` old (`store.FindFoundryAutomationEnded`), and walks queued runs a step at a time as their owner through `integration.SessionHost`. A fire's run and its cursor's move commit together, and a run's trigger key is unique per automation, so a fire runs at most once; an automation has at most one live run (an event waits for it, a schedule records a skipped run). An action step is marked executing before its call, so an attempt that dies in it leaves it failed, never run again; the run's lease (at least `config.MinAutomationLease`, twice an action's timeout) is renewed before every step. A `sync_connector` or `create_load` step then waits for its sync or load ("Waiting for the sync…"): the write that records it on the step (`foundry_automation_run_nodes.job_id`, `store.AwaitFoundryAutomationJob`) also marks the work as the run's, the run is handed back between reads (a tenth of the time taken, `step_wait` to a minute), a run picked up again after a restart waits on that job and never starts another, and the step ends as the work did (a sync that succeeded, a load ready or partial; else failed with why), or fails after an hour for a sync or 6 hours for a load, the work going on. A sync or load an automation's run started, by an action step or an action its Assistant step ran, names the run and how many automation runs led to it (`connector_syncs`/`foundry_loads.started_by_automation_run_id` and `automation_chain_depth`, migration `20261205000000_foundry_automation_causes.sql`), and a refresh load takes the cause of the sync that owed it (`foundry_ontologies.refresh_cause_*`); a run's trigger event carries the automations behind it (`caused_by_automations`, `chain_depth`). An event trigger skips work its own automation started, directly or through automations it set off, or past 3 runs in a chain, recording a skipped run that says why. An Assistant step whose thread has a live turn (its owner ran a card an earlier step left) waits for it. A skipped run keeps no spec, the worker deletes runs that ended over 90 days ago a batch at a time, and deleting an automation deletes its runs in batches too. An Assistant step queues a turn (`kind` automation) that the `foundry-agent-worker` runs, under `foundry.automations.monthly_usd` and `max_running`, apart from people's Assistant budget. A workspace keeps `max_per_workspace` automations and starts `runs_per_day` runs a day; a failed run holds the next back by `failure_backoff`, doubling; `pause_after_failures` in a row pause it and email its owner (`automation_paused`), and an owner who lost access pauses it (`store.PauseFoundryAutomationsOf`, for a host's member removal, and the worker when the owner's session is refused). A notify step queues an `automation_run` email for the `foundry-notify-worker`, which takes every link out of the Assistant's words (URLs, `mailto:`, email addresses, IP addresses and bare domains); a standalone install sends none.

The `foundry-automation-worker` (package `workers/foundry-automation-worker`, role `Roles.AutomationWorker`, with `foundry.automations.enabled`; a standalone install runs it) fires schedules due (one run however long it was due), finds each event trigger's ended work by a cursor over its target's own index, counted once `settle` old (`store.FindFoundryAutomationEnded`), and walks queued runs a step at a time as their owner through `integration.SessionHost`. A fire's run and its cursor's move commit together, and a run's trigger key is unique per workflow, so a fire runs at most once; a workflow has at most one live run (an event waits for it, a schedule records a skipped run). An action step is marked executing before its call, so an attempt that dies in it leaves it failed, never run again; the run's lease (at least `config.MinAutomationLease`, twice an action's timeout) is renewed before every step. An Assistant step whose thread has a live turn (its owner ran a card an earlier step left) waits for it. A skipped run keeps no spec, the worker deletes runs that ended over 90 days ago a batch at a time, and deleting a workflow deletes its runs in batches too. An Assistant step queues a turn (`kind` automation) that the `foundry-agent-worker` runs, under `foundry.automations.monthly_usd` and `max_running`, apart from people's Assistant budget. A workspace keeps `max_per_workspace` workflows and starts `runs_per_day` runs a day; a failed run holds the next back by `failure_backoff`, doubling; `pause_after_failures` in a row pause it and email its owner (`automation_paused`), and an owner who lost access pauses it (`store.PauseFoundryAutomationsOf`, for a host's member removal, and the worker when the owner's session is refused). A notify step queues an `automation_run` email for the `foundry-notify-worker`, which takes every link out of the Assistant's words (URLs, `mailto:`, email addresses, IP addresses and bare domains); a standalone install sends none.

How much an ontology helps a workflow is recorded as a use case's runs (`store/foundry_automation_workflows.go`, migration `20261203000000_foundry_automation_workflows.sql`, `agent/workflows.go`). Foundry makes one use case of each ontology a workflow uses (`foundry_workflows.automation_id`), named after it (kept in step as it is renamed) and counted in the ontology's 100: at the first run that uses the ontology, or when its owner approves steps that name it (an action's or an allowed action's `create_load`, a published dashboard's tiles; not what the trigger listens to). A run uses an ontology when an Assistant step calls a tool naming it (`ontology_id`, or a prepared action on it or on a dashboard that reads it) or an action step acts on it; its first use starts the run of that use case (`automation_run_id`, the owner's, its request the run's trigger and steps in words, `automation.Request`), and the Assistant step's reads and questions carry it as `use_case_run_id`, its id and its key (`foundry_workflow_runs.automation_key`, `FoundryWorkflowRun.Recording()`), which the agent loop sets for a workflow's turn and strips for every other, a helper's CLI turn's included: a model never names one, nor sees the field. The API records under such a run only a call naming its key, which no answer shows, so its id alone (on its pages and in `get_workflow_run`) records nothing for anyone, the owner's own agent included; once it is full or finished, those calls go on unrecorded. An action step is a use but no access: the access model records what an agent read of the ontology or sent to Foundry, and the engine's Assess takes reads, questions, sends and uploads only, so an action shows in the run's answer instead. The write that ends the workflow's run finishes its use case runs with what the run found (`FoundryAutomationRunEnd.Answer`), queueing their assessments, which the `foundry-ask-worker`'s Assess judges under its own cap; a cancelled run, or one its workflow's deletion ended, finishes them unassessed. A run that uses no ontology starts none; an ontology with 100 use cases leaves the workflow's runs there untracked (`foundry_automation_untracked`, which the workflow's read says). Only Foundry starts and finishes those runs (the API refuses, reason `FOUNDRY_WORKFLOW_OF_AUTOMATION`), and the use case is deleted only once its workflow is, which keeps it and its runs as history; deleting the workspace finishes the open ones unassessed. A grantee of source grants sees none of these use cases, their runs or their insights, as it sees no workflow: a workflow runs with its owner's access, so its runs may speak of sources the grantee wasn't granted. The use case's client token is its own, never one a person's use case can take. Workflows' and their runs' reads carry their ontologies (`FoundryAutomation.ontologies`, `FoundryAutomationRun.ontologies`), use cases their workflow (`FoundryWorkflow.automation`, `FoundryWorkflowRun.automation_run_id`), and insights count a workflow's runs apart from its owner's own (`FoundryWorkflowInsightSegment.automation`). No RPC was added.

The new workflow page offers suggestions written for one ontology's current version (`ListFoundryAutomationSuggestions`, `GET .../foundry/automation-suggestions?ontologyId=`, `api/automation_suggestions.go`; package `automation/suggest`; tables `foundry_automation_suggestions` and `foundry_automation_suggestion_ledger`, migration `20261204000000_foundry_automation_suggestions.sql`), at most 4, each a title, a prompt that only fills the composer, and an icon. The same callers as the other workflow routes. Until the Assistant has written them, and wherever it can't, they are the fallback from the version's competency questions (a weekly emailed answer to each of the first 4 with titles of their own, `suggest.Fallback`; none for a Definition v1). A read with no row, or one that failed an hour ago, queues a write (once per version, under the workspace's lock, 20 a workspace an hour) with the version's questions, so polls never read the version again, unless `foundry.agent.enabled` is off or the AI setting can't be used, and says `generating` while it is queued or running and was queued under 2 minutes ago. The `foundry-agent-worker` makes up to 3 writes at once, each under a 2-minute lease (3 claims at most); a write on the owner's own server (Ollama, an OpenAI-compatible one), whose calls the process queues, gets the setting's call timeout and renews its lease to match. A write whose version is no longer current ends failed. It reads the ontology's name, the version's types, links and questions, its generation's goal, title and connectors and the sets it reads (never data rows, every list and string capped, all of it in blocks the model is told are data), and makes one call on the workspace's extraction model (`llm.NewFor`, reasoning off), offering only the `suggest_workflows` tool and asking it to answer only by calling it, retried at most twice on an answer `suggest.Parse` keeps nothing of (no links, markup, ids, control or invisible format characters; titles 32 characters, prompts 400, unique), or, after a wait of 2 then 4 seconds, a refusal a retry may pass, all within 60 seconds. It writes nothing whose worst case the month's Assistant budget can't fit, and what every call spends is charged to that budget (people's pool) beside people's turns, in the ledger, whether the write ended, lost its lease or was cut short by the worker's stop (which leaves the row to its lease, unless the answer was in). The ledger also counts the hour's queues, and stays when rows go with their ontology. Rows go with their ontology and the workspace's work. A host registers the method in its authorization.

The MCP lists and gets workflows and their runs (`helix_foundry_list_workflows`, `helix_foundry_get_workflow`, `helix_foundry_list_workflow_runs`, `helix_foundry_get_workflow_run`) and prepares `create_workflow`, `update_workflow`, `pause_workflow`, `resume_workflow`, `delete_workflow` and `run_workflow`, which the Assistant prepares as cards too. A host that runs workflows registers the new FoundryService methods in its authorization, runs the worker where `integration.SessionHost` is provided, and calls `PauseFoundryAutomationsOf` in the transaction that removes a member.

## Agent integrations

`integration/` owns the Foundry MCP tool handlers and the ordinary HTTP Ask routes. It imports public Foundry contracts only. Hosts supply identity/authorization callbacks, database provisioning, durable confirmations and audit logging. Hosted Helix wires it into `mcpinsights`; the standalone binary registers it on its existing REST listener. Both use the existing API, question queue and workers.

HTTP clients POST `/v1/ontologies/{ontologyId}/ask` with a bearer, `Idempotency-Key` and `{"question":"..."}`, then GET the response's `Location` while it returns 202. Each call waits at most 25 seconds for a terminal question. A 200 includes `status` and the compact MCP result; it may be `cannot_answer`, `failed` or `cancelled`. Client disconnects do not cancel durable questions. See [the OpenAPI contract](../contract/foundry-integration.openapi.json), [the Python tool](../examples/ask_tool.py) and [local setup](../local/README.md#connect-your-agent).

The standalone install's confirmation table uses the directory's separate migration sequence. Hosted continues using its existing confirmation RPCs. Local setup supports connectors and documents, with API sources still disabled. `local/compose.yaml` publishes the install's listener on the host's loopback (`FOUNDRY_MCP_PORT` moves it): the Assistant's helper on the owner's computer reaches Foundry there, outside Docker. MCP, HTTP Ask and the helper's routes on it answer only for loopback, `host.docker.internal` and the host of `local.site_origin`, and refuse cross-origin requests; the site's routes are limited by the token, the helper's by tokens of their own.

Release the shared module first, then pin that commit in hosted Helix's Go/Bazel dependencies. For development across both checkouts, an untracked Go workspace can include each backend module; this does not replace the published module pin for CI. Hosted HTTP exposure uses `foundryAskHTTP.enabled` on the existing MCP ingress, enabled in development and disabled by default. No new DNS, TLS certificate, worker or ontology-agent release is needed. Publish immutable backend/site images and update the local Compose pins after testing.
